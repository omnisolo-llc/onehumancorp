# [backend] sqlite-vec Integration for Standalone Vector Search

## Title
sqlite-vec 🧠 (Standalone Desktop Vector Search Integration)

## Problem Statement
The OHC Hybrid Architecture relies heavily on `pgvector` for vector similarity searches in Cloud-Native (PostgreSQL) mode to support the AutoDream pipeline and Agent long-term memory. However, in Standalone Desktop Mode (SQLite), the application currently degrades gracefully to simple recency sorting or blob retrieval because a native vector search extension is not enabled. This disparity limits the Swarm Intelligence capabilities of locally running agents, meaning offline-first and edge-deployed agents cannot effectively query their consolidated memory using semantic embeddings.

## Research Report
- **Goal**: Integrate `sqlite-vec`, a vector search SQLite extension that runs anywhere, to provide native, fast semantic search capabilities in Standalone Desktop Mode.
- **Findings**:
  - `sqlite-vec` allows storing and querying vector embeddings directly within SQLite using familiar SQL syntax and virtual tables.
  - It avoids the need for external vector databases or complex in-memory approximate searches in Go, bringing SQLite closely in line with `pgvector`'s functionality.
  - By integrating `sqlite-vec`, local standalone clients can execute exact or approximate nearest neighbor queries (e.g., using cosine distance) on their episodic memory embeddings generated by local LLMs or cached from the cloud.
- **Competitive Analysis**:
  - Other approaches, such as building a custom Go-based KD-tree or loading embeddings into memory on startup, are memory-intensive and difficult to synchronize. `sqlite-vec` seamlessly integrates with SQLite's transactional model.
- **Architecture Validation**:
  - The current `srcs/server/db/migrations/` and `srcs/server/orchestration/autodream.go` explicitly skip vector similarity searches for SQLite.
  - Integration will require loading the `sqlite-vec` extension upon database connection initialization for SQLite pools and adjusting the AutoDream pipeline to use the appropriate SQL syntax for `sqlite-vec` when `IsSQLite()` is true.

## Design Doc
1. **Architecture Update**: Update the SQLite connection pool initialization in `srcs/server/db/sqlite_provider.go` to load the `sqlite-vec` extension.
2. **Database Schema**:
   - Modify the SQLite migrations (`srcs/server/db/migrations/*_autodream_pgvector_memories_sqlite.sql` or similar) to initialize a `vec0` virtual table for `consolidated_memory` embeddings.
   - A typical pattern would be creating a virtual table: `CREATE VIRTUAL TABLE vec_consolidated_memory USING vec0(embedding float[1536]);`
3. **API Contracts**: No external API changes. Internal query logic within `srcs/server/orchestration/autodream.go` will be updated to route vector queries to the `vec0` virtual table when the backend is SQLite.
4. **UI Wireframes**: Update the "Vector Memory Visualizer" to indicate whether it is connected to `pgvector` (Cloud) or `sqlite-vec` (Standalone).

## Implementation Prompt
"Implement `sqlite-vec` support for Standalone Desktop Mode vector searches.
1. Update `srcs/server/db/sqlite_provider.go` to load the `sqlite-vec` extension when initializing the SQLite connection pool.
2. Update the SQLite schema migrations in `srcs/server/db/migrations/` (specifically the autodream sqlite migration) to create a `vec0` virtual table linked to the agent memory embeddings.
3. Modify `srcs/server/orchestration/autodream.go` (and related pipeline logic) to execute `sqlite-vec` similarity queries (e.g., `knn` search) instead of skipping vector search when `dbProvider.IsSQLite()` is true.
4. Ensure 100% unit test coverage for the new SQLite vector search code path using `db.NewTestProvider(t)` and `db.RunMigrations()`.
5. Add an E2E test verifying that vector memories can be stored and retrieved using semantic similarity in a pure SQLite Standalone environment."
