# OHC Architecture Vision: The Agent-First Platform

## Introduction
To support the product vision outlined in the market research—specifically the pivot from "passive dashboards" to "proactive agents"—the underlying technical architecture of OneHumanCorp must be fundamentally different from traditional MVC (Model-View-Controller) SaaS applications. This document outlines the high-level technical paradigms required.

## The Traditional SaaS Flaw
Legacy platforms (Shopify, Wix) are essentially massive CRUD (Create, Read, Update, Delete) applications.
- The database is the source of truth.
- The UI (Dashboard) allows the user to mutate the database.
- The application logic is mostly passive, waiting for a user to click a button or a customer to place an order.
- This results in the "Dashboard Overwhelm" pain point.

## The OHC Paradigm: Event-Driven Agent Architecture

### 1. The Event Mesh as the Central Nervous System
Instead of a passive database, OHC must be built around a highly resilient, real-time Event Mesh (e.g., Kafka, NATS JetStream, or robust PostgreSQL logical replication/triggers).
- **Every action is an event:** A page view, an inventory decrement, a received Instagram DM, a failed payment.
- The state of the store is a projection of these events.

### 2. Autonomous Background Agents (The Workers)
Agents are specialized microservices or background workers that subscribe to specific topics on the Event Mesh.
- **The Support Agent:** Listens to the `inbox.message.received` stream. It utilizes an LLM (with RAG access to store policies) to attempt to generate a reply. If confident, it publishes an `inbox.message.send` event.
- **The Analyst Agent:** Listens to `order.created` and `traffic.page_view`. It aggregates this data overnight and publishes a `notification.briefing.ready` event at 8 AM.
- **The Operations Agent:** Listens to `inventory.level.changed`. If an item drops below a threshold, it publishes an `actionable_feed.item.created` event, asking the user if they want to reorder.

### 3. The 'Zero-Dashboard' Client
The mobile app (and web client) is no longer a complex form editor. It is primarily a client that consumes the `actionable_feed` stream.
- It displays pending decisions generated by the Agents.
- When the user taps "Approve", the client simply publishes a `decision.approved` event back to the mesh.
- The relevant Agent picks up that approval and executes the final API call (e.g., actually charging the credit card, or actually sending the email).

## Architectural Requirements for Engineering

To achieve this vision, the engineering swarm must prioritize the following non-functional requirements:

1. **Extreme Tenant Isolation:**
   - Agents will be querying data constantly in the background. RAG pipelines must be provably scoped so that Store A's Agent can never accidentally read Store B's customer data or API keys. Row-Level Security (RLS) in PostgreSQL is highly recommended.

2. **Idempotency Guarantee:**
   - Because events may be processed multiple times in distributed systems, every state-mutating API endpoint (especially payments and inventory) must be strictly idempotent.

3. **Low-Latency Push Infrastructure:**
   - For the "Unified Inbox" and "Activity Feed" to feel magical, WebSockets or Server-Sent Events (SSE) must be deeply integrated. When an AI auto-replies to an IG DM, the mobile app UI should update instantly without a manual pull-to-refresh.

4. **Observability of Agent Actions:**
   - When an LLM generates a response or makes a decision, the reasoning (confidence score, prompt used, tokens consumed) must be logged comprehensively. We need OpenTelemetry tracing that spans from the initial webhook, through the LLM call, to the final database write.

## Conclusion
By treating the AI not as a feature bolted onto a CRUD app, but as the core workers operating on an Event Mesh, OHC will deliver the "Invisible Agent" experience that our research proves the market desperately needs.
