# Recorded operations alerts and unsupported capabilities

## Implemented low-stock observations

`ProactiveOperationsWorker` only creates an observation when a persisted
`raw_materials` row has a positive configured reorder threshold and a recorded
quantity below it and an actual source timestamp/revision. Missing source
revisions are excluded because they cannot safely distinguish a later recurrence. The feed names that material, quantity and threshold and
retains its tenant, record ID and source revision. Acknowledging the observation
updates the feed decision; it does not claim to order inventory or contact a
supplier.

The alert ID hashes the tenant, material, source revision, quantity and threshold.
The database primary key and `ON CONFLICT DO NOTHING` enforce duplicate prevention
across concurrent workers and restarts. Previously acknowledged/dismissed source
versions are not recreated. Insertion rechecks the actual source row. Changed,
restocked or deleted source rows pause obsolete pending observations; existing
owner decisions are preserved. PostgreSQL source revisions use timestamp epochs,
so different connection timezones cannot duplicate the same observation.

The worker checks at most 100 tenants and 100 new material observations per tenant
per poll. Already recorded observations are excluded at the database, allowing
later batches to progress. Polling is at least 60 seconds, missed ticks are
skipped and a batch has a 30-second execution deadline. Each tenant has a
five-second total budget (including pool acquisition and context setup).
PostgreSQL transactions additionally use a one-second lock timeout and a
four-second statement timeout; these are transaction-local and do not change
other pool users' policy.

The in-memory tenant cursor advances **before** each attempt. Cancellation of a
partial batch therefore retains progress for the next poll; a slow early tenant
cannot repeatedly starve later tenants. Failed tenants are retried after the
ordered scan wraps. The cursor is not durable across process restarts; recorded
observations and database-enforced dedupe are durable. Failed reads/timeouts log
an incomplete scan rather than manufacture an empty/successful result. An
interrupted scan does not erase any observation already committed.

No unconfigured daily checklist is generated by `DailyOpsRoutineWorker`. Its
existing booking-history-based dormant-customer handling remains in place. Old
recorded feed entries are not deleted or retroactively labeled as verified.

## Explicitly open capabilities

The previous fixed supplier-delay, staffing-shortfall and daily-checklist claims
had no source facts or configured rule. They are not supported production alerts.
The worker reports those absences at startup. Genuine implementations need the
following persisted inputs and authorization rather than invented defaults:

- Supplier delay: a promised delivery timestamp/timezone, its source/provenance,
  line-level receipt status or received timestamp, cancellation state, and an
  owner-approved follow-up rule. A purchase order's creation time does not
  establish a promised delivery deadline.
- Staffing coverage: owner-approved coverage requirements by tenant, location,
  role and time interval, required staff count, timezone and rule revision,
  compared with actual eligible assignments and their current status. One
  scheduled person is not inherently a staffing shortfall.
- Scheduled checklist: an enabled tenant-owned routine definition with actual
  items, schedule/timezone, revision and standing authority, plus period-scoped
  routine instances and completion evidence. A new tenant is not a configured
  recurring routine.

These are open data/behavior contracts, not implemented capability claims. No
schema or default configuration is invented in this repair. The browser suite
keeps the existing controls covered with explicitly marked test-only recorded
operations proposals inside its guarded disposable database.

## Verification boundaries

The production-used `proactive_operations_storage.rs` module contains actual SQLite tests for empty/unconfigured accounts,
tenant isolation, concurrent/restarted worker dedupe, source changes, preserved
owner decisions, bounded batch progress and read errors. Source guards reject the
previous hardcoded production claims. PostgreSQL SQL must additionally be tested
against the real production-shaped tables, including conflict races and source
rechecks. The complete hosted Rust/browser gates remain acceptance criteria;
formatting and extracted SQL probes alone do not certify the compiled worker. A
source-linked minimal native probe can compile this storage module with real
PostgreSQL/SQLite pools and root-lock-matching dependency versions, without
fabricated application/database/cache implementations. Its result covers the
storage core. The production-used `proactive_operations_polling.rs` additionally
has cancellation/progress and total per-tenant deadline tests. The exact-source
native probe exercises both with actual PostgreSQL row locks: an outer timeout
retains the last attempted tenant, a later healthy tenant is processed, a locked
scan returns PostgreSQL55P03 within its budget, the failed tenant is retried on
wrap, and an existing APPROVED decision remains unchanged. Root worker auth/cache
wiring and hosted acceptance stay separate from this source-linked proof.
