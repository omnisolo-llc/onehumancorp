# Invitation creation and sharing boundary

The three maintained dashboard HTML copies load one adjacent, byte-identical `invite-bridge.mjs`. The previous duplicate listeners could issue two different invitation POSTs, copy twice, and open two share intents from one click. They also fabricated a fallback link on failure. The maintained control now calls the same-origin authenticated Next cloud-bridge endpoint once, with the verified session owner as the existing expected-owner header pair. The proxy strips browser-selected team and inviter identities and preserves the actual upstream status/body/URL. It never creates an invitation URL from an error or a failed GET.

The browser accepts only an unambiguous HTTP 200 invitation URL on the existing supported HTTPS invite hosts. The exact receipt is kept in the current view. Copy awaits the real clipboard promise; WhatsApp/X opens the same text as an intent and does not claim it was sent or that anyone joined. Account change, expiry, storage invalidation, and page exit retire visible private state and late UI completions.

Creation uses an origin Web Lock and writes an owner-bound operation marker before dispatch. Missing lock support, unreadable/corrupt history, or failed persistence blocks dispatch. Pending/uncertain outcomes remain held, including reload. A confirmed marker also holds another creation on reload. Only metadata is persisted: no invitation capability URL or authentication token is stored. This is browser-local duplicate prevention, not server idempotency or coordination across devices, origins, cleared storage, or unrelated invitation callers.

There is no safe reconciliation action in this UI. It tells the user to review existing invitations, but cannot adopt an old receipt or remove a pending marker. A bounded, authorized recovery workflow remains a capability gap. The current team-invite GET lookup and public invitation redemption flow were not certified by this repair; no automatic GET recovery was added. Other dashboard referral/milestone widgets and their legacy native calls remain separate scope.

Local proof uses the actual three HTML copies and modules in JSDOM, real Response/Headers objects, and recorded synthetic service/clipboard/window boundaries. Origin-lock behavior is modeled in unit tests, not certified as a real browser implementation. The Playwright CUJ requires the real authenticated local test backend, binds the UI to the actual receipt, counts the one creation request, checks real clipboard output and the outbound share intent, and verifies reload stays held. Browser execution remains a hosted verification gate; no live invitation account grant or social post was performed by these local tests.
