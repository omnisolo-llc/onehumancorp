# Onboarding draft ownership and interrupted saves

Onboarding verifies the current user and tenant before restoring an owner-scoped local draft. Legacy unowned and foreign-owner records remain held without being displayed or automatically uploaded. Authentication changes clear the visible view and pending timers; pending edits stay under their previously verified owner's key. Expected-owner request headers are concurrency preconditions, not authentication.

An origin Web Lock serializes draft and state writes for the same owner, across modern and maintained legacy pages. The lock spans dispatch and the complete validated acknowledgement body. Before dispatch, a durable local fence records the in-flight write. A crash, lost response, unreadable body, or ambiguous server result leaves the fence held. Later mutations cannot overtake it, and their acknowledgements cannot falsely mark newer edits clean. A read-only draft response has no authoritative version/receipt proving that an older unknown write stopped, so the UI does not clear this fence from an unversioned GET. It reports reconciliation required and preserves local edits. Explicit client rejection can release the fence without acknowledging the draft.

Without Web Locks or writable fence storage, draft mutations fail closed with a visible explanation. No racy localStorage lease substitutes for the origin lock. Each completed origin write advances an opaque local write generation, even for a stale or partial request. The generation is not a server CAS token and never clears an unknown fence. Acknowledgement is applied while the origin lock is still held; an older or no-snapshot completion cannot clean a newer local row. A matching acknowledgement marks only the exact current revision for the same owner and session epoch; newer local edits remain pending. Returning-owner pending local fields take precedence over older remote draft fields. Before merging a delayed remote read, setup rechecks the owner, session epoch, local draft/product snapshots, and completed-write generation. A new local-only revision holds restoration rather than overwriting those edits; same-owner remounts rehydrate a newer persisted revision. Protected preparation/launch receipts remain separate from editable state.

HTTP(S) legacy setup pages use the signed same-origin Next proxy. Raw file/custom-protocol setup has no certified authenticated transport and reports that limitation without network mutation. No bearer-token extraction, cross-origin credential fallback, CORS expansion, or new native auth command is added. This boundary does not claim that raw file pages or packaged native authentication have passed runtime certification.

Tests use deterministic origin-lock doubles and actual Response streams to cover reversed server commit order, delayed body consumption, two document contexts, crashes/reload, unknown outcomes, absent locks, storage failure, and auth invalidation. They do not replace real-stack/browser/native acceptance.

Scope: the gate covers the onboarding wizard, zero-click chat state, and maintained legacy setup pages. Other direct draft/state callers currently include website-builder, storefront-builder, and services/new; until migrated they do not participate in this origin write ordering. The local generation is not evidence of coordination with older clients, other devices, or arbitrary server writers.
