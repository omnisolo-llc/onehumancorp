# Builder draft ownership and save contracts

The website and storefront editors verify the current user and tenant before restoring private draft data. Their new local records use the same owner namespace and authentication lifecycle as onboarding. Older global keys remain held without being loaded or uploaded into the next account. Logout, account change, and a rejected owner precondition clear the visible state and fence late responses. Delayed server restoration also checks the exact local snapshot and local write generation before merging.

An origin Web Lock permits one active editor per owner and draft. Another view is held before hydration and editing; it must reopen after the first editor closes to load the latest saved revision. Unmount and owner invalidation release the lease, and the browser releases it when the document exits. Missing Web Locks hold editing visibly. Synchronous local writes under the lease retain edits before an authentication transition, while exact-row checks reject unexpected writes from an older client. Editor leases and short request locks use separate names, so saving never waits for its own editor lease.

A website editor with no local copy requires acknowledged, valid draft and state reads before opening an empty form. Failed restoration holds the view; it cannot replace an unseen remote draft with blank defaults. A retained local draft remains available when remote restoration fails. Draft saving and site saving have separate completion lifetimes, so one cannot strand the other's busy indicator.

Website setup details use the shared onboarding draft/state write gate. Only accepted setup fields are sent; editor layout and payment preference data remain in the local website draft. A local persistence failure holds automatic setup writes. Business setup continues through the canonical onboarding review and preparation/launch receipt flow; the website editor does not label a preparation response as a live business.

The onboarding API does not accept `builderState`. Storefront layouts therefore remain in verified-owner local storage, with an explicit local-save message and server-save limitation. The editor no longer posts a discarded payload or treats its HTTP success as layout persistence. Editor navigation does not rewrite the saved layout. Existing owner-local layouts take precedence over older remote setup fields.

The existing `POST /api/v1/builder/publish_draft` endpoint saves a site and then attempts an asynchronous publish job. Its HTTP 200 `{id, domain}` response proves a saved site, not a live deployment or working domain. Both editors require the actual site identifier and show that publishing is unverified; they do not invent a `/bio/myshop` or other public URL.

Before publication dispatch, an origin lock coordinates the owner’s requests and a durable owner-scoped marker stores the frozen request body. Missing, contradictory, incomplete, or unknown results remain held across reload, without an automatic retry. An explicit client rejection permits correction; a cached receipt prevents an identical resubmission but is not treated as fresh server acknowledgement. New edits made while an older request completes remain local and are labeled accordingly. The canonical session and server preconditions remain authority; local records and markers never authorize another tenant’s action.

The shared owner-bound business-action transport accepts only the explicit service-create, layout-generate, and site-save routes. It rejects redirects and uses same-origin credentials and no-store fetches. Service creation is a separate adapter to `POST /api/v1/booking/services`; a discarded `services` field in onboarding state is not a service-creation contract.

Scope: these are client and contract checks. Local generation markers do not provide server CAS, coordinate older clients or other devices, confirm publish-job completion, or certify a public website. Tests use synthetic identities, response streams, and origin-lock doubles; no provider or deployment transaction is executed during verification. Full repository and real browser/native acceptance remain separate gates.
