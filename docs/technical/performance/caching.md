# Hybrid Tiered Caching Strategy

Caching is the ultimate weapon against latency. OHC implements a sophisticated tiered caching strategy, encapsulated within the `HybridCache` utility, to protect underlying resources and ensure instantaneous data retrieval.

## 1. The `HybridCache` Architecture

The `HybridCache` is designed to be storage-agnostic, seamlessly transitioning between local in-memory storage (for Standalone deployments) and distributed Redis clusters (for Cloud multi-tenancy).

### 1.1 Lazy Initialization with `OnceLock`

To prevent caching infrastructure from slowing down the application startup, cache instances are lazily initialized using Rust's `OnceLock`.

```rust
static PRODUCTS_CACHE: OnceLock<HybridCache<Vec<Product>>> = OnceLock::new();

let cache = PRODUCTS_CACHE.get_or_init(|| HybridCache::new(redis_client));
```

This pattern ensures that the cache is only instantiated upon the first request that requires it.

## 2. Granular Time-To-Live (TTL) Policies

Not all data changes at the same rate. Applying a universal TTL results in either stale data or unnecessary database load. OHC defines specific TTLs based on the volatility of the underlying domain model.

### 2.1 Low Volatility (Long TTL)
*   **Organization State:** Cached for **3600 seconds (1 hour)**. Changes to the business name, tier, or domain are exceptionally rare.
*   **Product Catalog:** Cached for **3600 seconds (1 hour)**. Product metadata (name, description) updates infrequently. Inventory counts (which are highly volatile) are deliberately excluded from this cached aggregate to prevent overselling.

### 2.2 High Volatility (Short TTL)
*   **Recent Orders Summary:** Cached for **5 seconds**. Orders are constantly generated by AI agents and external webhooks. A 5-second TTL ensures the dashboard reflects near real-time reality while absorbing the impact of concurrent API spikes (e.g., multiple users refreshing simultaneously or a burst of webhooks).

### 2.3 Zero Volatility (No Cache)
*   **Transactional Verification:** Financial ledgers and inventory deductions bypass the cache entirely to guarantee strong consistency.

## 3. Cache Eviction and Invalidation

While TTLs handle eventual consistency, proactive invalidation is required for critical updates.

*   When a business owner updates a product via the UI, the specific cache key (`hub:products:{org_id}`) is explicitly deleted, forcing a fresh database read on the next request.
*   This hybrid approach (TTL + Proactive Invalidation) provides the optimal balance of speed and accuracy.

## 4. Impact on P99 Latency

The introduction of the `HybridCache` dramatically altered the latency profile of the platform. By absorbing repeated read requests, the database is freed to process writes and complex analytical queries without contention, flattening the tail latency curve even under extreme load.
