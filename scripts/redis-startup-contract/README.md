# Redis startup contract

Run `python3 scripts/focused_ci_gate.py redis-startup-contract` with the repository's Rust toolchain and an official `redis-server` binary on PATH. Run `bash scripts/redis-startup-contract/fetch.sh` once to prepare locked dependencies before offline execution; CI performs this step explicitly even on a cold runner. The gate is required by the PostgreSQL/security CI job and rejects missing, filtered, ignored or failing tests.

This harness compiles the production task queue module, exact startup preflight and queue-selection statements from `run_server`, the optional Redis pool, the actual standalone-mode accessor, and the builtin agent's timeout helper. A minimal DB carrier supplies the actual SQLite and PostgreSQL pool types without compiling the monolithic server. The legacy queue tests that opportunistically access ambient PostgreSQL are excluded at their module boundary; the unrelated in-memory-topic regression and all optional-pool tests remain included. This is focused source-bound evidence, not a full server build or end-to-end startup certificate.

Every configured hosted Redis queue must parse, connect/authenticate and answer PING within five seconds before database initialization or background workers start. Failure returns a credential-free error; it never silently changes queue backends. Standalone or absent Redis keeps the existing database-backed queue. A malformed rate-limiter URL remains an invalid startup configuration in either mode but now returns a safe error instead of printing the raw URL in a panic. The optional pool's disabled/invalid behavior stays unchanged.

The tests use process-isolated environment configuration, actual SQLite persistence, refused and silent owned loopback endpoints, and disposable authenticated Redis children on ephemeral loopback ports. They never contact public Redis or live queues. Each Redis child has its own temporary directory, no RDB/AOF persistence, and kill/wait cleanup on success or failure. The valid fixture verifies enqueue, reconstruction of the queue client, dequeue and completion. A concurrency case observes an actual blocked BLPOP through the owned Redis CLIENT LIST and proves enqueue/pruning still complete promptly on a separate cached socket. Both normal and blocking sockets are initialized within the same five-second startup deadline. Synthetic passwords are public fixture values; a separate canary checks errors and captured logs for leaks.

Limit: this does not repair runtime Redis reconnection or guarantee whole-server startup after readiness has passed. The later mesh transport creates its own connection and still needs a separately bounded per-attempt connection deadline. Configured Redis absence in cloud mode also retains the existing mesh policy; this gate certifies database queue selection, not that the whole cloud server supports a missing mesh endpoint.
