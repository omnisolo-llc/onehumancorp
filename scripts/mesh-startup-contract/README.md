# Bounded mesh startup contract

Run `bash scripts/mesh-startup-contract/fetch.sh` once to resolve/fetch root-locked dependencies, then `python3 scripts/focused_ci_gate.py mesh-startup-contract`. The required CI gate prepares dependencies before offline execution and rejects missing, ignored, filtered or failing tests. Rust and an official `redis-server` on PATH are prerequisites.

The harness compiles the entire production transport module before its legacy ambient-service tests, the actual builtin protobuf reexports, and the exact server startup call. It does not compile the monolithic server or substitute transport implementations. The controlled NATS endpoint is only an authentication-rejection fixture; it proves selection priority, Redis fallback and redacted logs, not successful NATS/JetStream operation.

Redis connection initialization has a five-second deadline. Cloud startup retains up to thirty attempts with one-second gaps; standalone retains one attempt and the existing optional transport fallback. A 180-second outer deadline bounds the full selected-transport operation, including a pending NATS connection. Fixed internal error variants distinguish invalid configuration, unavailability and connection timeout; the overall deadline has its own error. Redis startup diagnostics contain no URL, password or nested provider error. The pinned NATS connector logs raw rejection text and credential-bearing addresses; a future-scoped subscriber suppresses only its initial handshake diagnostics, followed by a fixed safe application warning on failure. A concurrent unrelated security-log canary must remain visible, including with DEBUG logging enabled. Post-connect NATS event logging is outside this focused certificate.

Tests use owned loopback sockets and disposable authenticated Redis children without RDB/AOF persistence. Redis children are killed/reaped and their temporary directories removed. Tests observe real handshake bytes and verify pending sockets close when the constructor, caller or overall deadline cancels. Retry/backoff and overall deadlines use Tokio's controlled clock; protocol/presence/locking/pubsub tests use actual Redis. A loopback proxy rejects the first connection and forwards the next to the owned Redis process, proving a later healthy retry works.

These are focused source-bound tests. They do not certify the full server build, hosted startup, live NATS success, runtime reconnect semantics, or subscriptions created after startup. No live endpoint or application queue is used.
