issue_title: "Implement Native Rust Omnichannel Chat System to Replace Chatwoot"
issue_description: |
  # Problem Statement
  OneHumanCorp (OHC) needs a unified inbox to process customer inquiries (DMs, emails, WhatsApp, etc.) securely and instantly. Currently, OHC lacks a native Rust omnichannel chat system and previously relied on external solutions like Chatwoot. To meet our strict Zero Trust, multi-tenant isolation, and mobile-first latency requirements, we must architect a native replacement within `onehumancorp/mono` that achieves feature parity with Chatwoot, ensuring the AI agent triage seamlessly intercepts and categorizes these conversations without human intervention, maintaining the "assistant-first" vision for our non-technical owner personas like Maya and Carlos.

  # Research Report
  - **Codebase Audit:** We discovered the legacy dependency has been fully retired. The `.chatwoot` source code audit reveals key entities needed: `Account`, `Inbox`, `Channel`, `Conversation`, `Message`, and `Contact`. Chatwoot uses separate models for different channel types (e.g., `Channel::WebWidget`, `Channel::Whatsapp`, `Channel::Email`).
  - **Competitor Analysis:** High-scale platforms like Shopify Inbox and Stripe use unified event streaming architectures. By building this natively in Rust, we can bypass external API overhead, leverage gRPC internally, and enforce Row Level Security (RLS) directly in our PostgreSQL schema based on `tenant_id`.
  - **Persona Fit:**
    - **Maya (Home Baker):** Receives Instagram DMs for cake orders. The native inbox must capture these instantly so the AI Sales Assistant can draft deposit requests.
    - **Carlos (Field Service Owner):** Needs WhatsApp messages converted into service requests. The unified inbox must work seamlessly on low-data connections (PWA mobile).

  # Design Doc
  ## Architecture & Data Model
  - **Tenancy:** Every record must have `tenant_id` for strict PostgreSQL RLS.
  - **Core Entities:**
    - `Inbox`: Aggregates conversations across channels for a specific tenant.
    - `ChannelAdapter`: Polymorphic configuration for specific platforms (WhatsApp API, Web Widget WebSockets, Email).
    - `Contact`: The customer interacting with the business, unified across channels via phone/email.
    - `Conversation`: A continuous thread between a `Contact` and the business via a specific `Inbox` and `ChannelAdapter`.
    - `Message`: The payload (text, media, attachments) within a conversation.
  - **AI Agent Integration:** New `Message` creation triggers the AI Job Queue (PostgreSQL `SKIP LOCKED`). The **Work Triage** agent intercepts the message, summarizes intent, and coordinates with other agents (e.g., Customer & Relationship Assistant to draft a reply).
  - **Real-Time Delivery:** Incoming webhooks from platforms (e.g., Meta) are processed via Rust axum/actix handlers, persisted, and then broadcast via WebSocket to the Flutter PWA.

  ## Mobile UX Flow (375px First)
  - **Unified Feed Screen:** The primary screen is the "Work Triage" feed, not a traditional chat list. Conversations appear as actionable cards.
  - **Conversation Card:** Shows customer name, platform icon (e.g., WhatsApp), a brief summary generated by the AI, and a suggested "Next Action" button (e.g., "Review Draft Reply", "Send Quote").
  - **Chat View:** Minimalist, translucent glass UI. Messages from the customer are on the left, agent/owner responses on the right. AI drafts are highlighted with a distinct visual token. Keyboard usage must not obscure the most recent message.

  # Implementation Prompt
  **Goal:** Implement the backend domain models, database schema migrations, and internal gRPC/REST APIs for the Native Rust Omnichannel Chat System.
  **CUJ:** A webhook from WhatsApp is received; the system identifies the tenant, creates/updates the `Contact` and `Conversation`, persists the `Message`, and enqueues an AI triage job. The OHC owner can then view this new message in the mobile web UI (Flutter).
  **Acceptance Criteria:**
  - Create PostgreSQL schema migrations for `Inbox`, `ChannelAdapter`, `Contact`, `Conversation`, and `Message` with `tenant_id` and RLS enabled.
  - Implement Rust structs and repository methods for these entities in `src/server/ohc/domain/chat` (or similar appropriate module).
  - Implement a webhook ingestion endpoint that securely processes incoming messages and stores them in the database.
  - Enqueue a new message event into the AI Job Queue.
  - Provide 100% unit test coverage for the repository and endpoint logic.
  - Include at least one Playwright E2E test verifying a mock webhook ingestion flow appearing in the unified inbox UI.
