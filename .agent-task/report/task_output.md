  # Research Report: The Unified Agent Feed

  ## Problem Statement
  Legacy business platforms require users to navigate complex, desktop-oriented dashboards. Our users (Maya, Carlos, Priya, Leo, Fatima, Nora, Jun) operate on the go, primarily from mobile devices (375px screens). They need a proactive system that tells them what requires attention and provides single-tap approval for complex actions, rather than making them search for tasks across multiple disconnected menus. The current mobile experience lacks a centralized, action-oriented "feed" for agent-proposed tasks.

  ## Research Report
  - **Competitive Landscape**:
    - Tools like Shopify and Wix have "companion apps," but they often require users to switch to a desktop web interface for complex setup (like managing variants, setting up discount rules, or creating advanced automation).
    - Link-in-bio tools (Linktree, Stan Store) excel because they offer simple, mobile-first interfaces, but they lack full business operation capabilities.
  - **OHC Differentiator**: OHC uses "Agentic Workflows" to handle complexity. Instead of building complex mobile forms, we use AI to propose actions (drafting an email, creating a product, responding to a lead) and present them as simple "Approval Cards."
  - **Findings**: The missing link in OHC is the central hub where all these agent proposals surface—a "Unified Agent Feed."

  ## Design Doc

  ### Architecture Diagram (High-Level)
  ```mermaid
  graph TD
      A[Various Event Sources: Stripe, Instagram, etc.] -->|Webhook/Internal Event| B(Event Ingestion Pipeline)
      B --> C{AI Intent & Context Layer}
      C -->|Draft Generation| D[Action Card Store / Feed DB]
      D --> E[Mobile App - Unified Agent Feed UI]
      E -->|User taps 'Approve'| F[Action Execution Engine]
  ```

  ### Mobile UX Flow (375px First)
  1. **Home Screen (The Feed)**: When the user opens the app, they immediately see a vertical scrolling list of "Action Cards".
  2. **Card Anatomy**:
     - **Context Header**: Who/What is this about? (e.g., "Customer Inquiry", "Inventory Alert", "Marketing Suggestion"). Color-coded by agent department (Operations, Sales, Customer Service).
     - **The Summary**: A brief, plain-language description of the situation (e.g., "Maya asked about vegan cakes on Instagram.")
     - **The Proposal**: The AI's suggested action or drafted response (e.g., "Drafted reply: 'Yes, we have 3 vegan chocolate cakes left! Should I hold one for you?'")
     - **Primary Action (Approve)**: A large, touch-friendly (>44x44px) button.
     - **Secondary Actions**: Smaller buttons for "Edit", "Discard", or "Ask Agent to revise".
  3. **Interaction**: Tapping "Approve" triggers the backend execution (sending the message, updating inventory), shows a brief success animation, and removes the card from the feed.

  ### AI Agent Integration Points
  - The feed consumes structured "Proposals" generated by the various domain agents (Operations, Marketing, etc.).
  - The feed UI needs to be agnostic to the specific *type* of action, rendering a standard template that can encapsulate different actions (text replies, state changes, etc.).

  ### Key Design Decisions
  - **Feed over Dashboard**: We are prioritizing a chronological, priority-sorted feed of actions over a static dashboard of metrics. Metrics are secondary to actions.
  - **Glassmorphism & OHC Tokens**: Use the OHC Premium Token library (translucent materials, clean hierarchy) to make the feed feel like a modern, premium assistant, not a clunky enterprise tool.

  ## Implementation Prompt (For Implementer Agent)
  **Objective**: Implement the front-end (Flutter/Web) and back-end (Go/Rust/DB) components for the MVP of the "Unified Agent Feed".

  **Critical User Journey (CUJ)**:
  1. An event occurs in the system (e.g., a mock webhook simulating a new customer message).
  2. The backend generates a corresponding "Action Card" (Proposal).
  3. The business owner opens the OHC mobile view (375px width).
  4. The owner sees the Action Card in their main feed, clearly describing the situation and the proposed response.
  5. The owner clicks the large "Approve" button.
  6. The system executes the action (simulated or real), provides visual feedback, and clears the card from the feed.

  **Acceptance Criteria**:
  - The feed UI must be perfectly responsive and optimized for a 375px width screen.
  - Must include at least 3 distinct types of mocked/test Action Cards (e.g., a message reply, an inventory alert, a marketing suggestion) to prove the generic UI handles different contexts.
  - Must use the OHC Design System (Premium Tokens, Glassmorphism).
  - The "Approve" interaction must be wired up end-to-end, hitting a real or test backend endpoint and successfully updating the UI state.
  - Must include Playwright E2E tests verifying the feed renders, cards are clickable, and the approval flow works on a simulated mobile viewport.
  - ZERO mock data in the final production code (use a proper seed script or API to generate the initial test cards for development).
