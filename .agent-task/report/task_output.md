  # Mission Queue Protocol: Offline-Tolerant Mobile POS & Agentic Ledger Sync

  ## Problem Statement
  Small business operators like Fatima (Food Cart Operator) and Priya (Boutique Owner) frequently operate in environments with flaky cellular connectivity, yet they need to process sales, update inventory, and manage multi-channel commerce (online vs. in-person) seamlessly. Traditional POS systems either fail offline entirely, block online sync, or create massive reconciliation headaches (double-booking). Existing platforms like Square or Shopify POS require technical intervention to fix sync conflicts. OHC must provide a localized, offline-tolerant POS flow that utilizes the Operations Agent to silently reconcile discrepancies, guaranteeing uninterrupted commerce on a 375px mobile UI.

  ## Research Report
  - **Market Context**: Our deep dive into the competitor landscape (e.g., `[research]_ohc_centralized_inventory_pos.md` and `[research]_ohc_smb_market_dynamics_agentic_workflows.md`) reveals that while Shopify and Square have strong POS capabilities, they rely heavily on third-party apps for advanced sync or simply fail gracefully when offline, leaving the owner to manually correct inventory counts later. Micro-SMEs often lack the technical know-how to resolve these conflicts.
  - **The OHC Opportunity**: Integrating a CRDT (Conflict-free Replicated Data Type) or robust Event Sourcing local-first architecture coupled with our AI Agent framework allows OHC to provide a zero-friction POS. When connectivity is restored, the POS syncs with the central Postgres ledger. If a conflict occurs (e.g., an online order and an offline order claim the last item), the Operations Agent intervenes to auto-draft an apology/refund or a supplier reorder, rather than crashing or showing a generic error.

  ## Design Doc
  ### Data Model & Sync Protocol (Architecture)
  - **Central Ledger (PostgreSQL)**: Serves as the ultimate source of truth. Uses `tenant_id` for row-level security.
  - **Local-First Client Cache (SQLite / IndexedDB)**: The Flutter/PWA client stores a localized copy of the catalog and inventory counts.
  - **Event-Sourced Sync Queue**: Offline POS transactions are recorded as immutable `SalesEvents` locally. When online, the client pushes these events to the OHC backend via a dedicated `/api/pos/sync` endpoint.
  - **Distributed Locks**: For online orders, Redis Redlock (`ohc:lock:{tenant_id}:inventory:{product_id}`) prevents concurrent online purchases but cannot prevent an offline POS sale.
  - **Agentic Reconciliation**: When the sync queue processes events, if the central ledger inventory drops below zero, an `InventoryConflictEvent` is published. The Operations Agent consumes this event, evaluates the scenario, and drafts an actionable resolution card for the owner's Agent Feed (e.g., "We oversold the Red Dress by 1. Should I cancel the online order or draft a rush supply order?").

  ### Mobile UX Flow (375px First)
  1. **POS View**: Clean, grid-based visual catalog with touch targets > 44x44px. An explicit, translucent status pill at the top shows "Offline Mode - Ready for Sales".
  2. **Checkout**: Tap-to-pay or cash recording occurs instantly with zero network delay.
  3. **Sync Feedback**: Once connectivity returns, a discreet progress ring completes, and the status pill turns green ("Synced").
  4. **Agent Feed Intervention**: If a conflict occurred, a high-priority "Action Required" card appears in the Agent Feed with 1-tap resolution buttons generated by the Operations Agent.

  ### AI Agent Integration Points
  - **Operations Agent**: Subscribes to `InventoryConflictEvent` and `LowStockEvent`. Uses tenant-scoped memory to determine preferred resolution strategies (e.g., Priya prefers restocking, Fatima prefers refunding).
  - **Customer Success Agent**: If an online order must be canceled, this agent automatically drafts the communication to the affected customer.

  ## Implementation Prompt
  **Target Persona**: Fatima the Food Cart Operator & Priya the Boutique Owner.
  **Outcome**: Implement the foundational backend sync endpoint, the `SalesEvent` ingestion pipeline, and the Operations Agent's conflict resolution logic. Ensure that when a POS client pushes a delayed transaction that results in negative inventory, the Operations Agent successfully catches the event and generates an actionable card in the Agent Feed.
  **Acceptance Criteria**:
  - A new API endpoint accepts batch `SalesEvent` payloads.
  - The backend correctly updates the PostgreSQL ledger and detects negative inventory scenarios.
  - The Operations Agent correctly intercepts the `InventoryConflictEvent` and generates a structured response card.
  - Full mobile-first E2E test verifying the flow from offline sale sync to Agent Feed card generation.
