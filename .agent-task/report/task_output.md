  # The Unified Agent Feed - Architecture & System Design

  ## Problem Statement
  Small business owners (our personas like Maya, Carlos, and Fatima) operate primarily from 375px mobile screens. Legacy platforms (Shopify, Wix) rely on complex, multi-page desktop dashboards. OHC’s core differentiator is "Invisible AI Automation"—where AI agents do the work, and the owner simply approves the results. Currently, we lack a centralized, mobile-first UX and underlying event-driven architecture to deliver these agentic proposals (e.g., drafted Instagram DMs, discount suggestions, automated marketing posts) in a unified, consumable format.

  ## Research Report
  - **Market Gap**: Competitors like Shopify offer basic mobile apps, but complex tasks (discounts, store design, automated marketing) still require desktop. Link-in-bio tools (Linktree) are mobile-first but lack business depth.
  - **The Solution**: An "Approval" interface paradigm. Instead of forms and toggles, the system pushes "Action Cards" to a vertical feed.
  - **Reference Research**:
    - `ohc_smb_mobile_first_design_research.md` (Identifies the 375px mobile MVP requirement and the "Approval" paradigm).
    - `agent_feed_deep_dive.md` (Outlines the Event Ingestion -> Intent Resolution -> Notification workflow).
    - `[research]_ohc_smb_mobile_first_agentic_workflows.md` (Validates the need for agents like "The Ambassador" and "The Promoter").

  ## Design Doc

  ### Architecture Diagram
  ```mermaid
  sequenceDiagram
      participant External as Webhooks / Triggers
      participant Ingestion as Event Ingestion (Redis/Kafka)
      participant Workers as Async Job Queue (pg SKIP LOCKED)
      participant LLM as Agent Orchestrator (Gemini/RAG)
      participant FeedDB as Feed Persistence (PostgreSQL)
      participant UI as Mobile UI (Flutter/PWA)

      External->>Ingestion: Incoming Event (e.g., IG DM, New Order)
      Ingestion->>Workers: Queue Event
      Workers->>LLM: Classify Intent & Draft Action
      LLM-->>Workers: Action Proposal (JSON)
      Workers->>FeedDB: Insert Action Card (tenant_id, status: pending)
      FeedDB-->>UI: Real-time update (WebSocket/Polling)
      UI-->>UI: User reviews on 375px screen
      UI->>FeedDB: User Action (Approve/Edit/Discard)
      FeedDB->>Workers: Queue Execution Task
      Workers->>External: Execute Approved Action (e.g., Send Reply)
  ```

  ### Mobile UX Flow (375px First)
  1. **Home Screen**: A vertical, single-column feed. Clean Ubiquiti UniFi style with translucent glass materials.
  2. **Card Structure**: Each "Action Card" contains:
     - **Context Icon/Color**: Indicates the agent (e.g., blue for Operations, purple for Marketing).
     - **Summary Text**: Plain language (e.g., "Drafted reply to @maya_cakes").
     - **Action Area**: Large (min 44x44px) touch targets for "Approve", "Edit", and "Discard".
  3. **Interaction**:
     - "Approve": Animates out, triggers background execution.
     - "Edit": Expands the card to show a native keyboard input for tweaking the draft.

  ### AI Agent Integration Points
  - **Event Hooks**: The feed must expose an internal API for any backend service to enqueue a `FeedItemProposal`.
  - **State Machine**: Feed items transition: `drafting` -> `pending_approval` -> `executing` -> `completed` / `dismissed`.

  ### Key Design Decisions
  - **Persistence**: Backed by PostgreSQL with row-level security (`tenant_id`). Allows for offline-tolerant reading and durable state if the app crashes during review.
  - **Agent Agnostic**: The feed payload must be generic enough (e.g., `{ type: "message_draft", content: "...", context: {...} }`) so that "The Ambassador", "The Promoter", or "The Advisor" can all push to it using the same core mechanism.

  ## Implementation Prompt (For Implementer Agent)
  **Feature**: Unified Agent Feed Backend & Core UI

  **Outcome**: Implement the foundational data model, internal API, and a basic Flutter/PWA UI for the Unified Agent Feed. The owner should be able to open the app, see a simulated/mocked action card generated by an internal trigger, and tap "Approve".

  **CUJ**:
  1. A background process (simulated for this task) inserts a `FeedItem` into the database.
  2. The owner logs into the OHC app (375px simulated mobile view).
  3. The owner sees the new Action Card in their feed.
  4. The owner taps "Approve" (button is at least 44x44px).
  5. The card's status updates in the UI and the backend database.

  **Acceptance Criteria**:
  - Define the `FeedItem` schema in PostgreSQL with proper `tenant_id` isolation.
  - Implement the gRPC/REST endpoints for the UI to fetch pending items and submit decisions (Approve/Dismiss).
  - Implement a basic Flutter/PWA vertical feed layout following mobile-first (375px) constraints and translucent design tokens.
  - Write E2E Playwright tests verifying the "Approve" flow from login to state change.
