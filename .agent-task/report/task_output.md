issue_title: "Native Rust Omnichannel Chat Engine (Chatwoot Replacement)"
issue_description: |
  ## Problem Statement
  OHC currently lacks a native omnichannel customer support and chat engine, having completely retired external dependencies like Chatwoot. Small-business owners like Maya (baker), Carlos (handyman), and Priya (boutique operator) need a unified inbox that aggregates Instagram DMs, WhatsApp, SMS, Web Widget, and Email inquiries. They need this unified inbox to handle customer context smoothly, auto-draft replies with AI agents, and seamlessly turn inquiries into bookings, quotes, and deposits.

  ## Research Report
  - **Chatwoot Source Code Audit:** Evaluated the Chatwoot GitHub repository (`https://github.com/chatwoot/chatwoot`), specifically focusing on `app/models/` and `app/models/channel/`. Chatwoot heavily relies on Ruby on Rails active record models mapping channels (e.g., `web_widget.rb`, `whatsapp.rb`, `instagram.rb`) and unifying them under `inbox.rb`, `conversation.rb`, and `message.rb`.
  - **Competitive Analysis:** Competitors like Shopify Inbox, GoDaddy Conversations, and Wix Inbox provide similar omnichannel experiences. However, they often lack native integrated AI agent departments (Operations, Sales, Finance) that proactively handle tasks based on conversation context.
  - **Identified Architectural Gap:** OHC needs a native Rust-based chat architecture utilizing a unified Inbox schema and Channel Adapters, deeply integrated with our AI job queues and multi-tenant Postgres architecture (row-level security with `tenant_id`).

  ## Design Doc
  ### Architecture Diagram (Mermaid.js)
  ```mermaid
  erDiagram
      TENANT ||--o{ INBOX : owns
      INBOX ||--o{ CHANNEL_ADAPTER : configured_with
      INBOX ||--o{ CONVERSATION : tracks
      CONVERSATION ||--o{ MESSAGE : contains
      CONVERSATION }o--|| CONTACT : involves
      CHANNEL_ADAPTER {
          string type "WebWidget, WhatsApp, Instagram, Email, SMS"
          json config
      }
      MESSAGE {
          uuid id
          uuid conversation_id
          uuid sender_id
          string content
          boolean is_ai_draft
          timestamp created_at
      }
      CONVERSATION {
          uuid id
          uuid tenant_id
          uuid inbox_id
          uuid contact_id
          string status "open, resolved, pending"
      }
  ```

  ### Mobile UX Flow (375px First)
  1. **Triage Feed:** The owner opens the app (375px screen). The home screen shows a combined feed of unread messages across all channels.
  2. **Conversation View:** Tapping a message opens a clean chat view. AI-suggested draft replies (generated by Customer Assistant) are presented as translucent glass suggestion chips above the native mobile keyboard.
  3. **Action Menu:** A prominent "+" button near the input field allows the owner to instantly convert the chat context into a "Quote", "Booking", or "Payment Link" via AI operations.
  4. **Status & Tags:** Swipe gestures on the conversation list allow quick marking as 'Done', assigning to staff, or snoozing.

  ### AI Agent Integration Points
  - **Work Triage Agent:** Hooks into `message_created` events. Analyzes intent. If standard support, drafts a reply. If it's a lead, notifies the Sales Agent.
  - **Sales & Revenue Assistant:** Can inject interactive widgets (quotes/payment links) directly into the `Message` thread for the owner to approve and send.
  - **Distributed Locks:** Redis Redlock (`ohc:lock:{tenant_id}:conversation:{conversation_id}`) ensures AI agents don't draft conflicting replies simultaneously.

  ### Key Design Decisions
  - **Unified Inbox Model:** All external channels map to a common `Message` and `Conversation` schema.
  - **Multi-Tenant Isolation:** Enforced via `tenant_id` on every table with Row-Level Security (RLS) in PostgreSQL.
  - **Asynchronous Processing:** Webhooks from WhatsApp/Instagram are ingested into a high-throughput queue (Postgres `SKIP LOCKED`) and processed asynchronously to ensure high availability and responsiveness.
  - **Rust Native Services:** Replacing Ruby-based Chatwoot with a high-performance Rust service inside `onehumancorp/mono`.

  ## Implementation Prompt
  **Outcome:** Implement the core domain logic, data models, and database schema for the Native Rust Omnichannel Inbox.
  **CUJ:** The user (e.g., Maya) receives a Web Widget message. The system must create a Contact, Conversation, and Message linked to her Tenant's Inbox. The Work Triage Agent must be triggered to evaluate the message.
  **Acceptance Criteria:**
  - Create the Postgres schema (with RLS for `tenant_id`) for `inboxes`, `channel_adapters`, `conversations`, `contacts`, and `messages`.
  - Implement Rust structs and repository traits for these entities.
  - Expose internal gRPC/REST APIs for ingesting a message from a channel webhook.
  - Add comprehensive unit tests and Playwright E2E tests verifying the message ingestion flow and multi-tenant isolation.
  - Ensure Zero UI mock data; all API responses must stem from the actual Postgres backend.
