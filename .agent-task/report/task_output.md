  # OHC Owner Work Assistant: Competitive Research & Agentic Solutions

  ## Problem Statement
  Small business owners and operators (like Maya the Baker or Carlos the Handyman) are overwhelmed by fragmented tools. They use scheduling apps, chat platforms (WhatsApp, IG DMs), and quoting software independently. AI assistants in the market are either too generic (ChatGPT) or too tightly coupled to a single domain (Shopify Sidekick for eCommerce), leaving service-based and omnichannel operators without a unified, proactive work assistant.

  ## Research Report & Deep-Dive Audit

  **Competitor Landscape (Top 10 General & Top 10 AI-Native):**
  - **General:** Tencent Workbuddy, WeCom, DingTalk, Feishu/Lark, Shopify Sidekick, Square Assistant, HubSpot AI, Notion AI, Microsoft Copilot, GoHighLevel.
  - **AI-Native:** Lindy.ai, Motion AI, Reclaim AI, Intercom Fin, MultiOn AI, Sierra AI, Decagon, Maven AGI, SynthFlow, Bland AI.

  ### Deep-Dive: Shopify Sidekick
  - **Capabilities:** Executes multi-step natural language commands for store configuration (e.g., "Put all winter items on 20% sale"), theme editing, and proactive sales analytics.
  - **Success Factors:** Deep native integration with Shopify's data schema; lowers the technical barrier for e-commerce operators.
  - **User Sentiment / Pain Points:**
    - "Great for basic reporting, but often fails at complex multi-step logical operations."
    - "Struggles with external tool integration outside Shopify."
    - "It's still a conversational interface; you have to know what to ask it."


  ### Competitive Gap Analysis Table
  | Feature / Capability | Shopify Sidekick | DingTalk | OHC (Proposed Agentic Feed) |
  | :--- | :--- | :--- | :--- |
  | **Core Domain** | E-Commerce configuration & themes | CRM, Chat, Approvals | Omnichannel Operations & Booking |
  | **Interface Type** | Chatbot conversational UI | Chat and Mini-Apps | Proactive Action Feed |
  | **Cross-Tool Automation** | Limited outside Shopify | Strong internal ecosystem | Deep via 'Draft-First' Entities |
  | **Approvals Flow** | Executed in chat immediately | Dedicated approval app | 1-Tap 'Approve & Send' Cards |
  | **Blank Canvas Mitigation** | Requires user prompting | Chatbot suggestions | High (Agents auto-draft actions) |
  ### Pain Point Synthesis
  1. **Fragmented Workflows:** Operators suffer from "tab fatigue." An AI that only knows scheduling is useless for quoting.
  2. **Blank Canvas Syndrome:** Text boxes are intimidating. Owners don't know the exact prompts to trigger complex workflows.
  3. **Lack of Autonomous Action:** Most AI tools suggest text. Owners need agents to *draft the actual business entity* (Quote, Invoice, Booking) and wait for a single "Approve" tap.

  ## Design Doc & Architecture

  ### Architecture: The "Draft-First" Agentic Feed
  To solve the "Blank Canvas" and "Lack of Action" pain points, OHC must shift from a Chat-first interface to an **Agent-Triage Feed**.

  ```mermaid
  graph TD
      A[Inbound Webhook/Message] --> B(Work Triage Agent)
      B --> C{Determine Intent}
      C -->|Sales| D[Sales Assistant: Drafts Quote]
      C -->|Support| E[Customer Assistant: Drafts Reply]
      C -->|Operations| F[Operations Assistant: Drafts Booking]
      D --> G[Unified OHC Triage Feed]
      E --> G
      F --> G
      G --> H[Owner 1-Tap Approval]
  ```

  ### UX Flow (Mobile-First 375px)
  1. **Home Screen:** A vertically scrolling list of "Pending Actions" generated by agents.
  2. **Card UI:** Each item shows: Context ("Maya asked for a vegan cake"), Proposed Action ("Drafted Quote for $45"), and two prominent buttons: [Approve & Send] or [Edit Draft].
  3. **Agent Visibility:** The UI clearly indicates *which* agent (Sales, Ops, Support) drafted the item, building trust over time.

  ## Implementation Prompt
  **User-Facing Outcome:** The user opens the OHC app and sees a prioritized feed of work items that agents have already triaged and prepared drafts for.
  **Critical User Journey (CUJ):**
    1. A mock inbound message is received via the API.
    2. The `WorkTriage` agent processes the message and creates a `PendingAction` record in the database.
    3. The owner opens the app (Mobile layout), sees the `PendingAction` card on the home screen.
    4. The owner taps "Approve", which executes the agent's proposed state change (e.g., sending an email or updating a booking status).
  **Acceptance Criteria:**
    - The feed must load in under 500ms.
    - The UI must be fully responsive at 320px-375px widths without horizontal scrolling.
    - The underlying database must support row-level tenant isolation for `PendingAction` entities.
