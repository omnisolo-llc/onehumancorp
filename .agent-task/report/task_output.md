issue_description: |
  # Problem Statement
  Small business owners (Carlos, Maya, Priya) currently face fragmented communication. While previous integrations relied on Chatwoot (which is now 100% RETIRED as an external service), they need a fully integrated, omnichannel support inbox inside the OneHumanCorp app. External tools break the "single pane of glass" and prevent the Ambassador (AI Customer Success agent) from natively orchestrating seamless follow-ups based on the user's unified OHC profile (e.g. past orders, invoices, service bookings).

  # Research Report
  **Chatwoot Source Code Audit:**
  - Audited `https://github.com/chatwoot/chatwoot`.
  - **Core Entities Identified:**
    - `Account`: The multi-tenant root entity.
    - `Inbox`: Aggregates messages for a specific channel.
    - `Channel::*`: Adapters for specific platforms (WhatsApp, SMS, Facebook Page, Email, WebWidget, etc.).
    - `Contact`: Represents the customer entity.
    - `ContactInbox`: Links a Contact to a specific Inbox.
    - `Conversation`: Links Contact/ContactInbox to an Inbox for an ongoing thread.
    - `Message`: Represents individual chat entries in a Conversation.
  - **Key System Architecture:**
    - Channels act as decoupled interfaces pushing structured data into `Conversations`.
    - `ContactInbox` acts as an identity bridge (`source_id`) between the platform's external identifier (e.g., a phone number) and the internal `Contact` entity.
    - OHC needs to replicate this model precisely in Rust, using `tenant_id` for row-level security and strong multi-tenancy.

  **Competitive Gap Analysis:**
  - Traditional unified inboxes (Shopify, Wix) aggregate but don't deeply automate. OHC will build an internal messaging fabric where the `Ambassador` AI agent reads inbound messages, references tenant inventory/scheduling data, and drafts contextual replies directly within the conversation stream before presenting it for owner approval.

  ### UI Wireframes & Mobile UX Flow (375px First)

  - **Mobile Inbox List:** UniFi-inspired cards showing active threads grouped by priority. Unread dots and channel icons (WhatsApp, Web, SMS) clearly visible.
  - **Thread View (375px):** Classic chat bubble layout. At the bottom, standard input field with a magic wand icon for the "Ambassador Draft".
  - **Translucent Glass UI:** Message drafts generated by AI have a slight blurred, frosted-glass highlight to distinguish them from human messages or sent messages.

  ### AI Agent Integration Points

  - **The Ambassador (Customer Success Agent):**
    - Subscribes to new `Message` creation events where `sender_type` is customer.
    - Queries the `Contact`'s omnichannel history and cross-references OHC's internal `Sales & Revenue` API.
    - Generates a new `Message` with status `draft`, placing it in the thread for the owner to review and tap "Approve".

  ### Key Design Decisions

  - **100% Native Rust Backend:** We will implement this as a set of Rust crates within `onehumancorp/mono`. We are not using Chatwoot or any Ruby external dependencies.
  - **Data Model:** Adopt Chatwoot's battle-tested `Account -> Inbox -> ContactInbox -> Conversation -> Message` structure, adapted for our PostgreSQL RLS `tenant_id` pattern.
  - **PubSub Realtime:** Rust microservices will use Redis Pub/Sub for real-time WebSocket event dispatch to clients (Flutter/PWA).

  # Implementation Prompt

  **User-Facing Outcome:** As an owner (like Carlos or Maya), I want all my customer messages (WhatsApp, Website Chat, SMS) to flow into a single unified inbox on my phone. The AI assistant should pre-draft context-aware replies for me to approve with one tap.

  **CUJ & Acceptance Criteria:**
  1. **Schema & DB Migration:** Implement PostgreSQL schemas for `inboxes`, `contacts`, `contact_inboxes`, `conversations`, and `messages` using strict `tenant_id` Row Level Security.
  2. **Core Rust Services:** Implement the core Rust gRPC/REST APIs to Create, Read, Update, and Delete these entities.
  3. **Channel Abstraction:** Implement a `ChannelAdapter` trait and provide a dummy/webhook implementation to ingest simulated inbound messages.
  4. **Frontend Inbox Shell:** Implement the 375px mobile Flutter/Next.js inbox view, connecting to the API and rendering threads and messages.
  5. Playwright E2E Tests: An owner logs in, navigates to "Inbox", sees a list of simulated incoming messages, opens a conversation, and successfully sends a reply. No mocked internal network calls. Data must persist through the stack.
