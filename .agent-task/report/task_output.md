  # The Unified Agent Feed: Actionable Mobile-First Notifications Architecture

  ## Problem Statement
  Currently, OHC platform lacks a centralized notification center where users (business owners like Maya or Carlos) can see actionable recommendations or drafts generated by background AI agents (like The Ambassador, The Promoter, or The Advisor). In the "Agentic Workflows" research, it was heavily emphasized that the SMB owner needs a proactive assistant, not just an admin panel. A unified "Agent Feed" is required to push Action Cards that the user can approve, dismiss, or edit from their phone without navigating complex menus.

  ## Research Report
  - **Context:** Multiple design documents and research files (`agent_feed_deep_dive.md`, `ohc_smb_mobile_first_design_research.md`, `[research]_ohc_smb_mobile_first_agentic_workflows.md`) describe an "Agent Feed" that serves as the "central nervous system".
  - **Gap:** While we have some backend APIs for agents (e.g., `assistant.rs`), the core architecture to reliably queue, prioritize, and surface Action Cards from multiple agents (events) to a unified mobile UI feed is missing.
  - **Competitive Advantage:** Shopify Sidekick is a reactive chatbot. Our Agent Feed makes OHC a proactive assistant. The system creates drafts/actions (e.g., responding to DMs, generating marketing posts) in the background and surfaces them as 1-tap "Approve" cards.

  ## Design Doc
  ### Architecture Diagram
  ```mermaid
  graph TD
      A[Event Sources: Webhooks, CRON, Internal State] --> B[Agent Event Bus (PostgreSQL SKIP LOCKED / Redis)]
      B --> C[Agent Workers: Ambassador, Promoter, Advisor]
      C --> D[Agent Feed Service (Rust)]
      D --> E[(PostgreSQL: agent_feed_cards table)]
      E --> F[API: GET /api/v1/feed]
      F --> G[Mobile Client 375px: Unified Feed UI]
      G --> H[Action: Approve/Dismiss/Edit]
      H --> I[Execute Action & Update Card State]
  ```

  ### Core Data Model (PostgreSQL)
  - **`agent_feed_cards` Table**:
    - `id` (UUID)
    - `tenant_id` (UUID, RLS enforced)
    - `agent_type` (Enum: Ambassador, Promoter, Advisor, etc.)
    - `card_type` (Enum: Actionable, Info, Alert)
    - `title` (String)
    - `description` (String)
    - `proposed_action_payload` (JSONB - e.g., `{ "action": "send_dm", "draft": "Yes we have vegan cake!" }`)
    - `status` (Enum: Pending, Approved, Dismissed, Edited)
    - `created_at` (Timestamp)
    - `updated_at` (Timestamp)

  ### Mobile UX Flow (375px view)
  1. User opens the OHC mobile app. The primary view is the "Today" feed.
  2. The feed displays Action Cards (translucent glass style, 16px border radius).
  3. A card from "The Ambassador" reads: "Customer asked about Vegan Cake. Reply: 'Yes, we have 3 left!'".
  4. At the bottom of the card are full-width, 44px high buttons: "Approve" (Primary, `#0066FF`) and "Edit" (Secondary).
  5. Tapping "Approve" executes the action via API, transitions the card state to Approved, and visually removes or collapses the card.

  ### AI Agent Integration Points
  - Background agents (e.g., `src/server/services/agent/*`) will use the new `AgentFeedService` to enqueue proposed actions instead of executing them immediately or sending standard push notifications.
  - The UI will render generic actionable cards based on the JSONB payload.

  ## Implementation Prompt (For Implementer Agent)
  **Feature Name:** Unified Agent Feed API & Data Model
  **Target Persona:** All OHC Owners

  **Outcome:** The implementer will create the core backend service and data model for the Agent Feed. This includes:
  1. Creating the PostgreSQL migration for the `agent_feed_cards` table (with row-level security).
  2. Building the Rust `AgentFeedService` module (`src/server/services/agent_feed/service.rs`) with methods to `create_card`, `list_pending_cards`, and `resolve_card` (Approve/Dismiss).
  3. Exposing these methods via Axum REST endpoints under `src/server/api/agent_feed_api.rs`.
  4. Ensuring 100% unit test coverage for the service and endpoints.

  *Note: Do not implement the frontend UI in this task. Focus strictly on the robust, multi-tenant backend foundation that allows any AI agent to push actionable cards.*
