  # Research Report: Offline-First Multi-Lingual Order Intake & Agentic Kitchen Display System (KDS)

  ## 1. Problem Statement
  Food and Beverage (F&B) micro-operators like Fatima (food cart owner) operate in highly constrained environments: limited English proficiency, chaotic physical spaces, and unreliable mobile data networks. Traditional POS and online ordering systems (e.g., Square, Toast) are often monolingual by default, require persistent high-speed internet, and rely on complex hardware setups. Fatima needs a resilient, multi-lingual, offline-tolerant system that runs on a low-end Android device to manage pre-orders, sold-out toggles, and daily prep lists.

  ## 2. Research Report
  - **Market Context**: Square and Toast dominate F&B, but their hardware and subscription costs are prohibitive for single food carts. They assume a stable connection and are often built for English-speaking staff. Shopify POS is robust but not optimized for F&B quick-service workflows.
  - **The OHC Opportunity**: OHC can provide an "invisible" tech stack where AI agents handle language translation on-the-fly and sync order state optimistically when the network is available. A simple, mobile-first KDS (Kitchen Display System) that works fully offline and syncs in the background will empower operators like Fatima to never miss an order due to poor connectivity.
  - **Competitor Gaps**:
    - *Square*: Excellent hardware, but offline mode has limitations on certain transaction types and lacks native agentic translation.
    - *Toast*: Expensive, hardware-heavy, and complex setup.
    - *Shopify POS*: Lacks native KDS features and food-specific workflows (prep times, modifiers).

  ## 3. Design Doc
  ### Architecture Diagram
  ```mermaid
  graph TD
      A[Customer Intake - Stripe/Web] -->|Order Received| B(Ambassador Agent - Translation)
      B --> C[Central Ledger - PostgreSQL]
      C --> D{Network Status}
      D -->|Online| E[Push to Local Ledger]
      D -->|Offline| F[Queue in Sync Worker]
      F -->|Connection Restored| E
      E --> G[KDS App - Low-end Android]
      G -->|Operator Updates Status| H[Local Ledger]
      H --> I{Network Status}
      I -->|Online| J[Push to Central Ledger]
      I -->|Offline| K[Queue in Sync Worker]
      K -->|Connection Restored| J
      J --> L(Manager Agent - Notification)
      L --> M[Customer Notified]
  ```

  ### Data Model & Sync Protocol (PostgreSQL & Local Cache)
  - **Local Ledger**: Acts as the primary write target for KDS actions (marking orders as preparing/ready) using a robust offline-first caching solution suitable for PWA/Flutter.
  - **Sync Queue**: A background worker that queues mutations and pushes to the Central Ledger (PostgreSQL) when online.
  - **Order Entity**: Includes `locale` (for translation), `prep_time`, and `status` (pending, preparing, ready, picked_up).

  ### AI Agent Coordination
  - **Customer Success Agent ("The Ambassador")**: Automatically translates incoming English pre-orders into the operator's native language for the KDS, and translates operator replies back to English for the customer notification.
  - **Operations Agent ("The Manager")**: Monitors order volume and automatically toggles high-demand items to "sold out" if the prep queue exceeds a predefined threshold, preventing overwhelming the operator.

  ### Mobile UX Flow (375px)
  1. **Order Intake (Customer)**: Multi-lingual photo menu. Customer selects items, pays via Stripe, and receives a confirmation.
  2. **Agentic Translation**: The system intercepts the order, translating notes and items into the operator's preferred language.
  3. **KDS View (Operator)**: High-contrast, large-touch-target (min 44x44px) list of active orders. Tapping a large button transitions state (e.g., "Ready for Pickup"). Works completely offline, caching changes locally.
  4. **Daily Summary**: A clear, easily readable daily order list generated by the Operations Agent.

  ## 4. Implementation Prompt
  **Feature Name**: Offline-First Agentic KDS & Multi-Lingual Order Intake

  **Target Persona**: Fatima the Food Cart Operator

  **Outcome**: Fatima receives translated pre-orders on her low-end Android device. She can manage her queue and toggle items out of stock even when mobile data drops out. The system automatically notifies customers when food is ready.

  **Next Actions**:
  1. Implement the local-first caching layer in the frontend KDS view to support offline order state transitions.
  2. Integrate the Customer Success Agent to automatically translate incoming order notes and items to the tenant's preferred locale.
  3. Build the 375px-optimized KDS UI with high-contrast, large touch targets for rapid, chaotic environments.
  4. Develop the background sync queue to reconcile local KDS state with the central PostgreSQL database once connectivity is restored.

  **Estimated Scope**: Medium
