  ### Title
  Architectural Design: Native Rust Omnichannel Inbox (Chatwoot Replacement)

  ### Problem Statement
  OmniSolo (OHC) currently lacks a native, high-performance omnichannel inbox that operates fully within our multi-tenant Zero Trust architecture. Relying on an external Chatwoot deployment introduces operational friction, latency, and breaks our strict tenant-isolation and mobile-first, offline-tolerant product promises. Maya (the baker) and Carlos (the handyman) need unified customer messaging (Instagram, WhatsApp, SMS, Web Widget) seamlessly embedded into their core OHC assistant, without managing third-party tools.

  ### Research Report
  - **Chatwoot Source Code Audit**: Reviewed `https://github.com/chatwoot/chatwoot`. Chatwoot utilizes a heavy Rails monolith with complex models for `inbox`, `conversation`, `message`, and various `channel/*` adapters (Email, Web Widget, WhatsApp, Instagram). Real-time communication relies on ActionCable via WebSockets.
  - **Competitor Systems Audit**: Systems like Shopify Inbox and Zendesk provide unified omnichannel experiences, but their architectures are decoupled from core operational work. A deeply integrated model allows AI agents to instantly draft replies based on operations data.
  - **Identified Gap**: OHC requires a native Rust implementation of Chatwoot's core omnichannel inbox features—specifically, unified multi-channel messaging (Instagram, WhatsApp, Web, SMS), WebSockets for real-time sync, and strict multi-tenant row-level isolation.

  #### UI Wireframes & Screen Flow Description (375px Mobile-First)
  - **Home (Work Triage)**: A clean, UniFi-style translucent glass card displaying "3 New Messages" with a breakdown by channel.
  - **Inbox View**: A unified, vertically scrolling list of conversations. No horizontal scrolling. Each row shows the contact's avatar, channel icon (e.g., WhatsApp), and a snippet of the latest message.
  - **Conversation View**: Chat bubbles. Native mobile keyboard support. A fixed bottom input bar. If offline, typed messages show a translucent "Sending..." state.
  - **AI Agent Integration Point**: An "AI Draft" button next to the send button. Clicking it instantly populates the input bar with a context-aware response generated by the Customer Assistant, utilizing tenant-scoped memory.

  #### Mobile UX Flow
  1. User (e.g., Maya) opens the OHC app (PWA/Flutter) on a 375px mobile screen.
  2. Tap "Inbox" on the bottom navigation.
  3. View unified list of DMs.
  4. Tap a conversation from a new lead asking about custom cakes.
  5. Tap "AI Draft". The input field fills with a polite reply including a quote estimate.
  6. Tap "Send".

  #### Key Design Decisions
  - **Zero Trust & Multi-Tenancy**: All database tables (`inboxes`, `conversations`, `messages`, `contacts`) enforce PostgreSQL Row-Level Security (RLS) on `tenant_id`. SPIFFE/SPIRE identity is required for service-to-service communication when delivering webhooks.
  - **Offline Tolerance**: Flutter client caches recent conversations via SQLite/Hive. Outbound messages are queued locally and synchronized with the Rust backend upon reconnection, using idempotency keys to prevent duplicate sends.
  - **Real-Time WebSockets**: A native Rust async WebSocket server (e.g., Axum or Actix) handles real-time message delivery, replacing ActionCable.

  ### Implementation Prompt
  **Goal:** Implement the backend Rust API and database migrations for the native Omnichannel Inbox (Conversations and Messages), replacing Chatwoot dependencies.
  **CUJ:** A non-technical owner (Maya) navigates to her Inbox, views a unified list of conversations from Web Widget and WhatsApp, taps a conversation, and successfully sends a reply.
  **Acceptance Criteria:**
  1. Create PostgreSQL schemas for `inboxes`, `channel_adapters`, `contacts`, `conversations`, and `messages` with strict `tenant_id` RLS.
  2. Implement native Rust backend REST endpoints (`GET /api/v1/inboxes`, `GET /api/v1/conversations`, `POST /api/v1/conversations/:id/messages`) for these entities.
  3. All endpoints must verify the tenant context via OIDC/SPIFFE identity headers.
  4. Implement an async WebSocket endpoint for real-time notification of new messages.
  5. Provide exhaustive Unit (100% coverage) and Bazel-executed tests for the new Rust module.
  6. Do not prescribe specific library implementations, but ensure endpoints are compatible with the OHC Flutter/PWA client and mobile 375px UX flows.
