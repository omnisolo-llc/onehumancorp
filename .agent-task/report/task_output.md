  # Research Report: Mobile-First Multi-Tenant Notification & Event Feed Architecture

  ## Problem Statement
  Small business owners and operators (Maya, Carlos, Priya, Leo, Fatima, Nora, Jun) rely on a multitude of events—new Instagram DMs, order confirmations, inventory low-stock alerts, AI agent drafted proposals, and system health checks. Currently, these events are disparate, forcing owners to hunt across different views or external apps to find what needs attention today. A core promise of OHC is: "Open OHC and immediately know what needs attention today." Without a centralized, real-time, agent-curated event feed, OHC fails its primary mission as a unified work assistant.

  ## Research Report
  **Findings & Competitive Analysis:**
  - **Tencent Workbuddy & WeCom:** Excel at unifying internal tasks, approvals, and system alerts into a single stream.
  - **Shopify:** Relies on push notifications for orders but lacks a unified, intelligent feed that prioritizes tasks (e.g., it doesn't surface "Drafted reply to customer X needs approval" alongside "Order Y needs fulfillment").
  - **Notion AI / Microsoft Copilot:** Great at context, but lack the immediate operational triage needed for a mobile-first field worker or baker.
  - **OHC Opportunity:** Implement an "Agent Feed"—a central nervous system where the Work Triage capability aggregates all system events (DMs, orders, bookings, AI drafts) and presents them as prioritized, actionable cards on a 375px mobile screen.

  ## Design Doc
  ### Architecture Diagram
  ```mermaid
  graph TD
      A[External Webhooks: Stripe, Instagram, etc.] -->|Ingest| B(Event Gateway / MsgBus)
      C[Internal Events: Order Created, Low Stock] -->|Ingest| B
      B --> D{Work Triage AI Agent}
      D -->|Classify & Prioritize| E[Tenant Event Feed DB]
      E --> F[Mobile-First UI / Flutter PWA]
      D -->|Trigger Specific Agent| G[Ambassador/Manager Agents]
      G -->|Draft Response/Action| E
  ```

  ### Mobile UX Flow (375px First)
  - **Home Screen (The Feed):** The primary view upon opening the app. A vertically scrolling list of Glassmorphism cards.
  - **Card Anatomy:**
    - **Header:** Source/Type (e.g., "Message", "Order", "AI Draft") with clear iconography.
    - **Body:** Concise summary generated by the Work Triage agent (e.g., "Sarah asked about vegan cakes. Drafted reply ready.").
    - **Actions:** 1-2 primary buttons (e.g., "Review Draft", "Approve", "Fulfill Order").
  - **Interaction:** Tapping a card expands it for more context or executes the primary action directly. Swiping dismisses non-critical informational alerts.

  ### AI Agent Integration Points
  - **Work Triage Agent:** Consumes raw events from the message bus. Uses LLM to determine priority (Urgent, Action Required, Informational) and generates a human-readable summary.
  - **Handoffs:** If an event is a customer inquiry, Work Triage passes it to the Customer Success Agent to draft a reply, then surfaces the draft back into the Feed for owner approval.

  ### Key Design Decisions
  - **Centralized Event Table:** A `tenant_events` table (PostgreSQL) using RLS for strict tenant isolation.
  - **Real-time Delivery:** Websockets or Server-Sent Events (SSE) to push feed updates to the active mobile client instantly.
  - **Action-Oriented:** The feed is not an audit log; it is a to-do list. Cards must have clear actions and disappear or change state once handled.

  ## Implementation Prompt
  **User-Facing Outcome:** When Carlos the field service owner opens the OHC app, he immediately sees his top priorities for the day: 1 new service request needing a quote, 1 overdue invoice to follow up on, and 1 AI-drafted reply to a customer question.
  **CUJ & Acceptance Criteria:**
  1. A backend service publishes a new generic event (e.g., `NewLead`) to the message bus for a specific `tenant_id`.
  2. The Work Triage Agent consumes the event, categorizes it, and inserts a record into the `tenant_events` table.
  3. The real-time update is pushed to the frontend.
  4. The mobile UI (375px) displays the new event as an actionable card at the top of the feed.
  5. Provide Playwright E2E tests: A user logs in, a simulated event is injected into the backend, the UI updates to show the new card, the user clicks "Acknowledge/Complete" on the card, and the card is marked resolved in the UI and database.
