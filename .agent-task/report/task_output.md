  ## Title: AI-Driven Project Intake & Proposal Generation

  ## Problem Statement
  Service-based businesses, independent professionals, and agency principals (e.g., Nora) lose hours translating messy client inquiries—from emails, social DMs, and quick phone notes—into structured project scopes and professional proposals. Existing platforms like HoneyBook and Dubsado are form-heavy, rigid, and assume the owner is sitting at a desktop building complex templates. They do not proactively structure unstructured demand, creating a significant bottleneck for non-technical operators trying to capture leads from their phones.

  ## Research Report
  - **Competitive Analysis - HoneyBook & Dubsado**: Both platforms dominate the creative and service SMB space, but their mobile apps function mainly as read-only dashboards. To create a proposal, the owner must manually input client details, select a template, and adjust pricing.
  - **Competitive Analysis - Notion AI / HubSpot**: Notion provides flexible text generation but zero native billing or operations workflow. HubSpot is too enterprise-focused and lacks seamless 375px mobile-first execution.
  - **The Gap**: OHC currently lacks an autonomous intake-to-proposal pipeline. There is no system to take a raw voice note or fragmented DM (e.g., "Client wants a 5-page website and logo design by next month") and instantly generate a ready-to-send, branded proposal with integrated payment terms.

  ## Design Doc

  ### Architecture Diagram
  ```mermaid
  graph TD
      A[Raw Intake: DM, Form, or Voice Note] --> B(Work Triage Gateway)
      B --> C{Operations Agent}
      C -->|Analyze Scope & Timeline| D[Project Schema DB]
      C -->|Draft Scope| E{Sales & Revenue Agent}
      E -->|Calculate Pricing & Terms| F[Proposal Engine]
      F -->|Generate Draft| G[Mobile Action Feed 375px]
      G -->|Owner Taps 'Approve'| H[Stripe Payment Link / PDF]
      H --> I[Dispatch to Client]
  ```

  ### UI Wireframes & Mobile UX Flow (375px First)
  - **Screen 1 (The Feed)**: Owner opens the app and sees an Action Card: *"New Inquiry: 5-Page Website for Smith Corp. Drafted proposal ready."*
  - **Screen 2 (Proposal Review)**: Tapping the card opens a translucent glassmorphism preview of the proposal. The screen is vertically scrolling. It includes:
    - Client Info (auto-extracted).
    - Scope of Work (bulleted list generated by AI).
    - Investment (Pricing table with an auto-calculated total).
  - **Screen 3 (Action Bar)**: A sticky bottom bar (min height 54px) with a primary button `Approve & Send` and a secondary button `Edit Terms`.
  - **Edit Flow**: If the owner taps `Edit Terms`, they don't get a complex WYSIWYG editor. Instead, they get a conversational AI input: *"Increase price by 10% and add a rush fee."* The proposal updates instantly.

  ### AI Agent Integration Points
  - **Work Triage Agent**: Parses incoming multi-channel messages to identify high-intent project inquiries.
  - **Sales & Revenue Agent**: Responsible for drafting the actual proposal copy, querying past successful proposals for pricing context, and integrating Stripe payment links for the deposit.
  - **Operations Agent**: Automatically sets up internal project tasks and placeholders in the database once the proposal is sent and approved.

  ### Key Design Decisions and Why
  - **Conversational Editing over WYSIWYG**: Mobile WYSIWYG editors are historically frustrating and prone to breaking layout. By using conversational AI for edits ("Make it 2 weeks instead of 3"), the owner stays in a simple chat interface while the agent handles document formatting.
  - **Action-Card Paradigm**: Proposals aren't hidden in a "Documents" tab. They are surfaced immediately in the unified agent feed because they represent revenue blockers.
  - **Translucent Glass UI**: Follows the OHC Premium Token library with blur-heavy, layered cards to present complex information clearly without visual clutter.

  ## Implementation Prompt
  **User-Facing Outcome:** Nora receives an email from a prospect. She forwards it to her OHC assistant email (or it's auto-ingested). She opens her OHC app to find a fully formatted proposal waiting in her feed. She taps "Approve & Send," which sends the client a beautiful web link containing the scope and a Stripe deposit form.

  **CUJ & Acceptance Criteria:**
  1. Ingest a mock unstructured client inquiry (text or JSON payload).
  2. The AI Agents must extract the client, scope, and generate a pricing estimate based on tenant history or standard rates.
  3. The drafted proposal must appear in the Mobile UI feed as an Action Card.
  4. The proposal preview UI must be perfectly responsive at 375px wide.
  5. The "Approve & Send" action must create a valid Stripe Payment Link and update the proposal state to `Sent`.
  6. E2E Playwright tests must verify the intake parsing, mobile rendering, and the approval mutation flow. Do not use mocked UI state; data must persist through the real API.
