  # Mission Queue Protocol: Native Rust Omnichannel Chat System

  ## Problem Statement
  OHC requires a lightning-fast, highly scalable omnichannel customer support and chat engine natively built in Rust. Relying on an external service like Chatwoot breaks our deep multi-tenant isolation model (Zero Trust, SPIFFE/SPIRE), introduces external latency and reliability issues, and creates friction for AI Agent integrations (Operations, CS, Marketing). Non-technical owners like Maya (Baker) and Carlos (Handyman) need a seamless, invisible system that immediately triages WhatsApp DMs, Web Widget inquiries, and email, letting our AI assistants draft responses and coordinate tasks behind the scenes, all accessible on a 375px mobile viewport without complex configuration.

  ## Research Report & Feature Benchmarking
  **Benchmarking Target:** `https://github.com/chatwoot/chatwoot`
  An audit of Chatwoot's source code architecture reveals key components that must be replicated natively in Rust:
  1. **Data Models:** By auditing `app/models/inbox.rb` and `app/models/message.rb`, it is clear that Chatwoot heavily depends on Active Record polymorphism (e.g. `channel_type`, `channelable`). We must replicate:
     - `Account` -> `Tenant` mapping in OHC.
     - `Inbox` mapped to `Tenant` to configure assignment rules and CSAT.
     - `Channel` adapters mapping to `Inbox`. (Like `Channel::WebWidget`, `Channel::Whatsapp`).
     - `Conversation` and `Message` entities mapped to a `Contact`.
  2. **Omnichannel Inbox & Conversations:** Grouping messages from WhatsApp, Web Widgets, SMS, and Email into unified threads based on polymorphic channel adapters.
  3. **Channel Adapters:** Webhook processors for Meta/WhatsApp Business API and WebSocket handlers for live Web Widgets.
  4. **Real-time Messaging:** WebSocket-based event broadcasting to connected clients (agents/owners), similar to ActionCable in Chatwoot.
  5. **Agent Routing & SLAs:** Rules for assigning conversations to specific human or AI agents (replicated natively using our Redis distributed lock and AI Job Queue).

  **Competitive Analysis:**
  - **Shopify Inbox / Wix Inbox:** Deeply integrated into the respective platforms. By building natively, OHC can achieve even deeper integration with our AI Job Queue (PostgreSQL SKIP LOCKED) and Redis distributed locks for agent coordination.
  - **Performance:** A native Rust implementation (using Tokio, Axum/Tonic, and SQLx) will deliver superior latency, reduced memory footprint, and perfect alignment with our existing K8s deployment model compared to Chatwoot's Ruby on Rails monolith.

  ## Design Doc: System Architecture

      }

  ### Mobile UX Flow (375px First)
  1. **Unified Triage Feed (Home):** The owner opens the OHC app. A clean, Apple/Ubiquiti-style translucent card displays "3 New Messages" aggregated from WhatsApp and the Web Widget.
  2. **Conversation View:** Tapping the card opens a chat thread. The UI is native, utilizing the full 375px width. Touch targets for "Approve AI Draft", "Reply Manually", and "Create Order" are 44x44px minimal.
  3. **AI Assistance (Invisible):** If the customer asked "Do you have vegan cakes?", a draft reply generated by the CS Agent is already waiting. The owner taps "Send Draft".
  4. **Offline Tolerance:** If the owner is on a slow connection, the reply is queued locally and optimistic UI instantly updates the thread.

  ### AI Agent Integration Points
  - **Trigger:** New incoming `MESSAGE` records trigger a PostgreSQL `NOTIFY` or push a job to the AI Job Queue (PostgreSQL `SKIP LOCKED`).
  - **Triage & Classification:** The *Work Triage Agent* categorizes the message intent (e.g., Lead, Support, Order Inquiry).
  - **Drafting:** The *Customer & Relationship Assistant* (Gemini Pro) analyzes tenant memory/context and drafts a response.
  - **Coordination:** Redlock (Redis) ensures multiple AI workers do not attempt to reply to the same message simultaneously.

  ### Key Design Decisions
  - **Multi-Tenancy:** Strict row-level security (RLS) in PostgreSQL enforced by passing `tenant_id` claims through SPIFFE/SPIRE JWTs down to the database connection context.
  - **Real-time:** Use Axum WebSockets for the frontend and Web Widget to broadcast events (e.g., `message.created`, `conversation.updated`).
  - **Extensibility:** The `CHANNEL` model uses a `provider_type` and polymorphic adapters in Rust, making it trivial to add Email or SMS later.

    - 5 Playwright E2E tests simulating the customer sending a message and the owner viewing it on a 375px viewport.
    - All existing and new `main` branch tests (`bazel test //...`) MUST pass.
