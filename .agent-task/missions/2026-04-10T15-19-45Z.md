# Title
Implement KAIROS Orchestration: Shared Task List, Teammate Mesh, and AutoDream

# Problem Statement
The OHC Hybrid Agentic OS requires a cohesive orchestration layer to manage the AI Agent Swarm with absolute autonomy. The system lacks a consolidated integration between the Shared Task List (distributed state machine), the Real-time Teammate Mesh (communication layer), and the AutoDream Pipeline (long-term memory consolidation). Without this KAIROS orchestration triad, the agents cannot orchestrate deeply-deliberated architectural changes or reliably prevent worker collisions in multi-tenant environments.

# Research Report
1. **Codebase Analysis**: Foundational implementations exist within `srcs/server/orchestration/`.
   - `TaskOrchestrator` handles task queueing and acquisition.
   - `StateMachine` tracks entity state changes (e.g., PENDING -> IN_PROGRESS).
   - Database migrations `013_shared_tasks.sql`, `025_kairos_dag_deps.sql`, and `027_state_machine_transitions.sql` define the persistence layers.
   - Real-time messaging uses `MeshMessage` structures via Redis/Centrifuge.
2. **Market Context**: Competing agentic frameworks often fail at durable state persistence across crashes. The OHC Hybrid Architecture (OHC-HA) uniquely targets a cloud-native K8s deployment (PostgreSQL + Redis) with a seamless degradation path to a standalone desktop experience (SQLite).
3. **Requirement Synthesis**: We must unify these components into a single `KAIROS` orchestration service that exposes real-time APIs for agent coordination, manages task locking, and asynchronously pipelines completed execution summaries into the AutoDream vector database.

# Design Doc

## Architecture & Data Flow

1. **Shared Task List (The Brain)**:
   - **Schema Details**: Tasks reside in `shared_tasks`, dependencies in `task_dependencies`, and transitions in `state_machine_transitions`.
   - **Concurrency Model**: In PostgreSQL mode, use `SELECT FOR UPDATE SKIP LOCKED` for task claiming. In SQLite standalone mode, utilize application-level mutexes (`sync.Mutex`).
   - **Sequence Diagram (Task Claiming)**:
     ```mermaid
     sequenceDiagram
         participant Agent
         participant TaskOrchestrator
         participant StateMachine
         participant DB
         participant TeammateMesh
         Agent->>TaskOrchestrator: AcquireReadyTask(capabilities)
         TaskOrchestrator->>DB: SELECT FOR UPDATE SKIP LOCKED
         DB-->>TaskOrchestrator: Task details
         TaskOrchestrator->>StateMachine: Transition(PENDING -> IN_PROGRESS)
         StateMachine->>DB: UPDATE shared_tasks & INSERT state_machine_transitions
         StateMachine->>TeammateMesh: Broadcast(State Change)
         TaskOrchestrator-->>Agent: Assigned Task
     ```

2. **Teammate Mesh APIs (The Nerves)**:
   - **Transport Layer**: Real-time events broadcast via Redis Pub/Sub (`rueidis`) and WebSocket via `CentrifugeNode`.
   - **Event Contracts**: Messages MUST strictly follow the `MeshMessage` structure: `agent_id`, `action`, `status`, `sender_id`, `role`, `content`, `timestamp`.

3. **AutoDream Pipeline (The Memory)**:
   - **Ingestion**: Upon task completion (`CompleteTask`), the orchestrator queues an asynchronous job.
   - **Compression & Embedding**: The sub-agent invokes Minimax LLMs to compress session logs into a concise summary and generates a `[]byte` vector embedding (native mapping for SQLite compatibility).
   - **Persistence**: Results are stored in `swarm_long_term_memory` (using `pgvector` indexing in PostgreSQL).
