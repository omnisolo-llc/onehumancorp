# Title: Shared Task List - KAIROS Orchestrator Architecture

## Problem Statement
The OHC Hybrid Agentic OS requires a robust "Shared Task List" mechanism to support KAIROS Orchestrator functionality. High-level feature requests need to be decomposed into shared tasks, tracked across multiple agents via a distributed state machine, and properly synced between Standalone Mode (SQLite) and Cloud-Native Mode (PostgreSQL). We need to architect the proper DB schemas, concurrency locks, and sequence diagrams so implementer agents can execute the logic safely.

## Research Report
- Current `tasks_db.go` has initial support for `ClaimTask` using `SELECT FOR UPDATE SKIP LOCKED` for PostgreSQL and an application-level mutex for SQLite.
- The `shared_tasks` table is defined in `013_shared_tasks.sql` and `025_kairos_dag_deps.sql`.
- Missing is the deep-deliberation "UltraPlan" logic and comprehensive statemachine transition broadcasting logic to ensure the Teammate Mesh stays in sync.
- Competitive Analysis: Typical microservices use BullMQ/Celery, but OHC requires an internal db-backed state machine for durability without heavy external dependencies in standalone mode.

## Design Doc
1. **Database Additions**:
    - Improve `shared_tasks` to handle robust priority and payload structures.
    - Define robust schemas for state machine transitions in `state_machine_transitions` table.
2. **Architecture Diagram**:
    ```mermaid
    sequenceDiagram
        participant UltraPlan
        participant TaskOrchestrator
        participant SharedTasksDB

        UltraPlan->>TaskOrchestrator: Decompose(HighLevelTask)
        TaskOrchestrator->>SharedTasksDB: Insert(SubTask1, SubTask2)
        SharedTasksDB-->>TaskOrchestrator: Success
        TaskOrchestrator->>TaskOrchestrator: BroadcastNewTasks()
    ```
    - Centralized `TaskOrchestrator` handles KAIROS decomposition.
    - Redis Pub/Sub (Teammate Mesh) notifies agents when a `shared_tasks` row status changes from `PENDING` -> `ASSIGNED` -> `COMPLETED`.
    - Local fallback: simple long-polling or lightweight events when Redis isn't available.
