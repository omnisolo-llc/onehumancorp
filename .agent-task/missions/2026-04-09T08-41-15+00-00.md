# Title: Analyze Local SQLite Concurrency and Throttling Strategy

## Problem Statement
In Standalone Desktop Mode, the local agent swarm interacts with a shared SQLite database (`swarm.db`). Under burst workloads, this leads to severe `database is locked` errors due to host I/O constraints and lock contention, as standard exponential backoff mechanisms become quickly exhausted.

## Research Report
The existing `DelegateMission` logic lacks mode-aware concurrency throttling. While Cloud-Native mode handles high concurrency via scalable API nodes and PostgreSQL, Standalone mode requires a defensive approach. The research confirms that we must strictly throttle parallel agent writes to SQLite when `OHC_STANDALONE=true` is set. This trades raw throughput for zero-error stability, which is critical for local desktop environments where hardware constraints are rigid.

## Design Doc
1. **Throttling Mechanism:** Introduce a concurrency limiter (e.g., using a Go channel or semaphore) within the `DelegateMission` function or a centralized Standalone task queue.
2. **Configuration:** The concurrency limit should be configurable but default to a conservative value (e.g., 1 or 2 concurrent writes) when in Standalone mode.
3. **Telemetry Integration:** Ensure that metrics related to queue depth and throttling duration are recorded in the local metric buffer for future cloud sync and observability.

3. Add appropriate tests to verify that concurrency is correctly limited in Standalone mode but remains unconstrained in Cloud-Native mode.
