# Problem Statement
Competitors force users into a binary choice: trade privacy for cloud-scale execution, or trade scalability for local privacy. The OHC platform bridges this divide, allowing seamless operation switching. However, the current architecture lacks an "Offline-to-Cloud State Sync for Swarm Memories". A critical gap exists where local SQLite RAG state cannot be synchronized to the cloud Postgres orchestration engine via OHC-SIP when scaling up workloads that require massive parallel computation over local contexts.

# Research Report
- **Competitive Landscape**: Claude Code indexes only local directories. OpenClaw and Replit Agent index only what is in the cloud and fail entirely offline.
- **Current OHC State**: True Hybrid (K8s Cloud & Standalone Local) execution mode. Postgres & SQLite SIPDB Local/Cloud Sync mechanism is fundamentally there but lacks the RAG protocol layer.
- **Architectural Gaps**:
  1. No daemon or process selectively synchronizes local SQLite RAG state (like `swarm_memory_embeddings`) into the cloud's `agent_missions` table.
  2. No secure protocol to delegate generalized tasks to the K8s multi-tenant cloud without exposing raw private datasets.

# Design Doc
### 1. Hybrid-Native MCP RAG Synchronization Daemon
A new Local-to-Cloud Context Synchronizer daemon that bridges SQLite Standalone and Postgres Cloud environments for secure RAG context delegation.
- Reads from `swarm_memory_embeddings` or `autodream_memories`.
- Strips sensitive PII locally before uploading.
- Publishes sanitized context payloads to a cloud REST endpoint.

### 2. Orchestration Escalation
When local MCP agents determine a task requires scaled compute, the daemon invokes an OHC-SIP Cloud Sync.
- A new `agent_missions` entry is created in the Cloud Postgres DB.
- K8s Pod Orchestration processes the multi-tenant cloud swarm.
- Computed results are synced back to the Standalone Desktop SQLite database.

**Instructions:**
1. **Daemon Implementation**: Create `srcs/server/orchestration/rag_sync.go`.
2. **Logic**:
   - Implement a polling/event-driven daemon `StartRagSyncDaemon(ctx context.Context, hub *orchestration.Hub)`.
   - The daemon should periodically query local SQLite (`hub.DB().IsSQLite() == true`) for unsynced RAG state/memories that are marked for cloud escalation.
   - Sanitize payloads to remove PII.
   - Sync the sanitized payloads into the Cloud Postgres `agent_missions` table or a specific memory endpoint.
3. **Database Additions**:
   - Add a `cloud_sync_status` column to `autodream_memories` if it doesn't exist, to track which memories have been escalated.
4. **Testing**:
   - Write tests in `srcs/server/orchestration/rag_sync_test.go`.
   - Test offline local indexing, the sanitization logic, and the cloud sync mock. Achieve >90% coverage for the daemon.

**Acceptance Criteria:**
- Daemon correctly identifies and synchronizes local RAG state to the cloud.
- PII sanitization is functional and tested.
- Integration tests verify the end-to-end sync without breaking standalone mode.
