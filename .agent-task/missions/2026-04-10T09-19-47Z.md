Title: "Master Architecture: KAIROS Orchestration, Teammate Mesh, and AutoDream Memory"
Problem Statement: "The OHC Swarm lacks a unified orchestration layer (KAIROS) to decompose features, a resilient realtime communication mesh (Teammate Mesh) for pub/sub coordination, and a long-term memory consolidation pipeline (AutoDream). Without these, complex autonomous operations fail to coordinate securely and scale across Cloud-Native and Standalone deployments."
Research Report: "Our hybrid architecture dictates dual modes. Cloud-Native mode utilizes PostgreSQL with `FOR UPDATE SKIP LOCKED` for task concurrency, Redis (`rueidis`) for horizontally scalable pub/sub via Centrifugo, and `pgvector` for exact Nearest Neighbor semantic search. Standalone Desktop mode degrades to SQLite with application-level mutexes for transaction isolation, memory-backed or SQLite-backed mesh transport, and fallback text search if vector extensions are unavailable. `CLAUDE_OHC.md` confirms this architectural split. We must implement background workers for AutoDream to consolidate session data into `autodream_memories`."
Design Doc: |
  # KAIROS Unified Orchestration Design

  ## 1. Shared Task List (Phase 1)
  **Database Schema (PostgreSQL/SQLite):**
  ```sql
  CREATE TABLE IF NOT EXISTS shared_tasks (
      id TEXT PRIMARY KEY,
      organization_id TEXT NOT NULL,
      parent_plan_id TEXT,
      title TEXT NOT NULL,
      description TEXT,
      status TEXT NOT NULL DEFAULT 'PENDING',
      assigned_agent_id TEXT,
      dependencies JSONB,
      created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
      updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
  );
  CREATE INDEX IF NOT EXISTS idx_shared_tasks_org_status ON shared_tasks(organization_id, status);
  ```

  **Sequence Diagram (Task Claiming):**
  ```mermaid
  sequenceDiagram
      participant Agent as Worker Agent
      participant DB as Postgres (shared_tasks)
      participant Hub as Teammate Mesh Hub

      Agent->>DB: BEGIN
      Agent->>DB: SELECT id FROM shared_tasks WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED LIMIT 1
      alt Task Found
          DB-->>Agent: Returns Task 123
          Agent->>DB: UPDATE shared_tasks SET status = 'ASSIGNED', assigned_agent_id = 'worker-1' WHERE id = 123
          Agent->>DB: COMMIT
          Agent->>Hub: Publish MeshEvent {topic: 'task.assigned', payload: Task 123}
      else No Task Found
          DB-->>Agent: Returns 0 rows
          Agent->>DB: ROLLBACK
      end
  ```

  **Architecture:**

    ```protobuf

      string event_id = 1;

    ```
  - **Transport Layer:** `srcs/server/orchestration/hub.go` integrates `CentrifugeNode`. Implements `RedisMeshTransport` (via `rueidis`) for Cloud-Native and `MemoryMeshTransport` for Standalone.

  ## 3. AutoDream Data Pipelines (Phase 3)
  **Vector Storage Schema (pgvector):**
  ```sql
  CREATE EXTENSION IF NOT EXISTS vector;
  CREATE TABLE IF NOT EXISTS autodream_memories (
      id TEXT PRIMARY KEY,
      organization_id TEXT NOT NULL,
      agent_id TEXT,
      content TEXT NOT NULL,
      embedding vector(1536),
      source_type TEXT NOT NULL,
      created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
  );
  CREATE INDEX IF NOT EXISTS idx_autodream_org ON autodream_memories(organization_id);
  ```
  **Workflow:** Background `AutoDreamWorker` sweeps completed `shared_tasks` and memory contexts (`.agent-task/memory/*.yml`), generates embeddings via LLM client (`srcs/server/agents/local/llm.go`), and upserts into `autodream_memories` (batching with `LIMIT 500`).
