# 📊 Mission: Address Sub-Agent Orchestration Bottleneck in Cloud vs Standalone Modes

## Problem Statement
The OHC Hybrid Architecture (OHC-HA) is experiencing inconsistent throughput during high-concurrency sub-agent task delegation. In Cloud-Native Mode (K8s, PostgreSQL), the `TaskOrchestrator` suffers from connection pooling saturation and lock contention under load, while in Standalone Desktop Mode (SQLite), concurrent writes are leading to `database is locked` errors during state transitions. This discrepancy causes unpredictable agentic autonomy and breaks the seamless hybrid experience.

## Research Report
*   **Context:** Sub-agents are spawned rapidly by the Swarm to handle complex tasks, relying on the central OHC-SIP (Swarm Intelligence Protocol) database.
*   **Cloud-Native Insights:** Prometheus metrics show `pgxpool` exhaustion and increased latency in `ClaimTask` and `UpdateTaskStatus` due to row-level contention.
*   **Standalone Insights:** Execution data indicates that SQLite's WAL mode is enabled, but application-level mutexes in `TaskOrchestrator` are too coarse, serializing all orchestration operations even when not strictly necessary.
*   **Gap Analysis:** We lack specific metrics for lock wait times and task state transition latencies broken down by Hybrid mode.

## Design Doc
1.  **Metric Instrumentation:** Introduce OpenTelemetry histograms for `orchestrator.lock.wait.duration` and `orchestrator.transition.duration`, tagged with `hybrid_mode` (cloud/standalone).
2.  **PostgreSQL Optimization:** Refactor `ClaimTask` to utilize `FOR UPDATE SKIP LOCKED` more efficiently, possibly batching claims or utilizing a lightweight advisory lock if row contention is too high.
3.  **SQLite Optimization:** Refine the mutex strategy in `TaskOrchestrator` for Standalone Mode. Move from a single global mutex to finer-grained locking or utilize SQLite's built-in capabilities to allow concurrent reads while writes are serialized.
