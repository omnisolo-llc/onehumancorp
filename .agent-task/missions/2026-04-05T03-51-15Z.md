# 🔬 Researcher: [Core Architecture] Implement Hybrid MCP RAG Protocol (Local-to-Cloud Context Synchronizer)

**Priority**: P0
**Estimated Scope**: Large

## 1. Problem Statement
Competitors force users into a binary choice: trade privacy for cloud-scale execution, or trade scalability for local privacy. The OHC Hybrid Architecture (OHC-HA) has a structural advantage, but currently lacks the robust mechanism to seamlessly escalate and synchronize highly sensitive Local SQLite Swarm Memories up to the Cloud Postgres orchestration engine when massive parallel computation is required.

## 2. Research Report
- **Competitive Gap**: Claude Code indexes only local directories, OpenClaw/Replit index only what is in the cloud. They fail to handle offline-to-cloud scalable degradation gracefully.
- **Current State**: The foundation exists in the `agent_missions` schema and `db.Provider`. However, the automatic escalation and background sync mechanism from Local Standalone Mode to Cloud-Native Mode is missing.
- **The "Blue Ocean" Delta**: Implementing a unified **"Hybrid MCP RAG Protocol"** will allow users to process highly sensitive datasets entirely via local standalone Desktop mode. When tasks require scaled compute, the local client securely delegates generalized tasks to the K8s multi-tenant cloud without exposing the raw private dataset, syncing only required context payloads into the cloud's `agent_missions` table.

## 4. Implementation Prompt
As the Implementer agent, your mission is to build the Hybrid MCP RAG Protocol synchronization engine.

1. **Local Sync Daemon**:
   - Create a background worker (e.g., in `srcs/server/orchestration/sync_daemon.go`) that queries the local SQLite `agent_missions` table for tasks that are marked for cloud escalation (e.g., status `ESCALATING` or via a specific `escalate_to_cloud` boolean flag).
   - *Constraint*: Always include a `LIMIT 100` clause in your background sync loop `SELECT` query to prevent memory explosion.
   - *Constraint*: For Standalone mode resilience, HTTP calls syncing payloads to the cloud must implement exponential backoff retries to handle transient network unavailabilities (use `context.WithTimeout` and a custom retry closure).

2. **Payload Sanitization**:
   - Before syncing, ensure `rag_context` or other explicit PII markers are strictly stripped from payloads to preserve data privacy. Only generalize context payloads should be sent.
   - Use the `X-OHC-Conflict-Resolution: force-local` header when interacting with the Cloud API to govern local state overwrite precedence.

3. **Cloud API Reception**:
   - In `srcs/server/api/` (or equivalent HTTP routing layer), add a route and handler for `POST /api/sync/missions` to receive this payload and insert/upsert it into the Postgres `agent_missions` table.
   - *Constraint*: When implementing database UPSERT logic using `db.Provider` where custom programmatic fallback is required (e.g., checking `force-local` headers), use a basic `INSERT` query and catch the error. Check the error for 'duplicate key value' or 'UNIQUE constraint failed' to manually execute the `UPDATE` query. **Crucially, because Postgres aborts transactions on error, you must use SAVEPOINTs (e.g. `SAVEPOINT before_insert`, and `ROLLBACK TO SAVEPOINT before_insert` on error) before falling back to the UPDATE query.** Do not use native `ON CONFLICT DO NOTHING/UPDATE` as it swallows the error preventing the custom logic.
   - Reuse `http.Client` instances across requests to enable connection pooling.

4. **Testing & Validation**:
   - Write unit tests for the background worker and the API handler. Maintain strict test coverage >90%.
   - Ensure the new routes are protected with appropriate Auth middleware.
   - Execute `bazelisk test //...` to ensure all tests pass.
