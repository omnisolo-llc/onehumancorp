# Architecting AutoDream: Long-Term Memory Consolidation Pipeline

## Problem Statement
OHC Agents generate vast amounts of short-term episodic memory (chat transcripts, intermediate thoughts, file diffs) during task execution. Without a mechanism to consolidate this data, agents lose context over time, and querying past interactions becomes inefficient. We need "AutoDream"—a pipeline to continuously process episodic memory into long-term embedded vector truth (semantic search).

## Research Report
- **Goal:** Architect the data pipelines for OHC's long-term memory consolidation system using LLM embeddings and a Vector DB.
- **Context:**
  - Episodic memory is currently stored in standard relational tables or JSON logs.
  - Target: We need vector representations of these memories for semantic retrieval (RAG).
  - Environment: Cloud Mode uses `pgvector` in PostgreSQL. Standalone Mode might use `sqlite-vss` or a simpler local embedding index if native vector extensions aren't viable, or just standard SQLite full-text search as a fallback.
- **Key Pipeline Stages:**
  1.  **Extraction:** Identify new or modified episodic memories.
  2.  **Summarization/Structuring (Optional):** Use an LLM to extract key facts, decisions, and codebase insights from raw transcripts.
  3.  **Embedding:** Generate vector embeddings for the structured facts using an LLM API (e.g., OpenAI `text-embedding-3-small` or a local model).
  4.  **Storage:** Upsert the text and vectors into the Vector DB.

## Design Doc
### Vector Schema (pgvector)
We will leverage `pgvector` for the primary cloud implementation.
Table: `ohc_memory_embeddings`
- `id` (UUID)
- `tenant_id` (UUID/TEXT)
- `memory_type` (TEXT, e.g., 'CODE_INSIGHT', 'TASK_SUMMARY', 'USER_PREF')
- `content` (TEXT, the actual summarized fact)
- `embedding` (VECTOR(1536))
- `created_at` (TIMESTAMP)
- `source_task_id` (UUID/TEXT, reference to the task that generated it)

### The AutoDream Background Worker
We need a background process (the "Dreamer" daemon) that runs periodically or in response to "task complete" events:
1.  **Trigger:** Task is marked `DONE`.
2.  **Gather:** Fetch all episodic logs/chat messages for that task.
3.  **Synthesize:** Call the LLM to summarize: "What are the key technical decisions, user preferences, and permanent facts from this session?"
4.  **Embed:** Call the embedding API on each extracted fact.
5.  **Persist:** Insert into `ohc_memory_embeddings`.

### Architecture Component
Create `srcs/server/memory/autodream/pipeline.go`.
Define an interface `MemoryConsolidator` that wraps this logic.

## Implementation Prompt
**Title:** Implement AutoDream Memory Consolidation Pipeline

**Instructions:**
1.  **Database Migration:** Create a DB migration to add the `ohc_memory_embeddings` table with pgvector support (`CREATE EXTENSION IF NOT EXISTS vector;`). Ensure graceful degradation or alternative schema for SQLite.
2.  **Vector Repository:** Create `srcs/server/memory/vector_repository.go` with methods to Upsert embeddings and perform Semantic Search (Cosine similarity or L2 distance).
3.  **AutoDream Service:** Create `srcs/server/memory/autodream/service.go`. Implement the pipeline: fetch task logs -> call LLM (use existing LLM provider interfaces) to summarize -> call Embedding API -> store in Vector Repository.
4.  **Wiring & Triggering:** Wire the AutoDream service into the `TaskHandler` so that when a task transitions to `DONE`, an asynchronous AutoDream job is dispatched (using the Sub-Agent Queue or a simple goroutine for v1).
5.  **Testing:** Write unit tests mocking the LLM and Embedding APIs. Verify the data flow from raw text to vector storage.

Ensure robust error handling (retries for rate-limited LLM APIs) and metric tracking (e.g., `autodream_facts_consolidated_total`) via OpenTelemetry.
