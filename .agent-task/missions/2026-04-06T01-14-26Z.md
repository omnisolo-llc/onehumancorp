# Title: Architect Highly Available Teammate Mesh APIs & Distributed Sub-Agent Queuing

## Problem Statement
The current `TeammateMesh` implementation uses a `LegacyTeammateMesh` which depends on bare WebSockets and Redis pub/sub. Meanwhile, task coordination across the swarm lacks a highly scalable background queuing logic that maps seamlessly to the `SharedTask` lifecycle, resulting in race conditions when scheduling isolated sub-agents in a multi-tenant Cloud environment versus a Standalone SQLite setup.

## Research Report
1. **Current State:** `srcs/server/orchestration/mesh.go` implements a standard WebSockets interface, but it lacks the robust guarantees (e.g. at-least-once delivery, backpressure) needed by KAIROS to orchestrate thousands of sub-agents concurrently. `srcs/server/orchestration/tasks.go` utilizes PostgreSQL `SKIP LOCKED` for queue distribution, but the interaction with the real-time mesh is decoupled and prone to desynchronization.
2. **Competitor/Market Analysis:** Modern Agent OS platforms (like AutoGPT, BabyAGI, and LangGraph) employ durable distributed state machines (e.g., temporal.io or BullMQ) combined with gRPC or resilient streaming.
3. **OHC Constraints:** The OS must run in Hybrid Mode (both high-scale K8s/Postgres/Redis and single-machine SQLite). Temporal is too heavy for Standalone mode.

## Design Doc
### Architecture
1. **Teammate Mesh API Layer (v2):** Deprecate bare WebSocket and transition entirely to a resilient interface via `CentrifugeNode` (already partially integrated in `TaskBroadcast`). Create structured Go channels wrapping Centrifuge's events.
2. **Distributed Sub-Agent Queue:** Implement an interface `SubAgentQueue` backed by two adapters:
   - *Cloud-Native Mode:* A robust background queuing implementation utilizing `rueidis` to maintain a sorted set (ZSET) for scheduled sub-agents.
   - *Standalone Mode:* Polling directly from a new SQLite `sub_agent_queue` table with application-level mutex coordination.
3. **State Machine Tracking:** Tie the Teammate Mesh directly to the `SharedTask` lifecycle. When a task transitions (`PENDING` -> `IN_PROGRESS`), the State Machine emits a guaranteed sequence of state events over the new Mesh APIs.

### API Contracts
* `POST /api/mesh/v2/broadcast` - Accepts `MeshMessage` payload, validated and broadcasted via Centrifuge.
* `POST /api/queue/subagent` - Enqueues a task payload.

### Database Schema Changes
* `sub_agent_queue` table (ID, ParentTaskID, Payload, Status, ScheduledAt, CompletedAt).

## Implementation Prompt
1. In `srcs/server/orchestration/mesh.go`, build the `V2TeammateMesh` struct that fully utilizes `CentrifugeNode` instead of bare websockets. Ensure backward compatibility by keeping `LegacyTeammateMesh` for now.
2. Add a `SubAgentQueue` interface in `srcs/server/orchestration/queue.go` with `Enqueue`, `Dequeue`, and `Complete` methods.
3. Implement `PgRedisQueue` (using Rueidis ZSETs) and `SqliteQueue` (using the database Provider with `sync.Mutex`).
4. Update `TaskManager.PollTasks` to utilize the new State Machine tracking to dispatch `MeshMessage` events correctly and durably.
5. Provide comprehensive unit tests (`srcs/server/orchestration/mesh_v2_test.go` and `queue_v2_test.go`).
6. Apply OHC Glassmorphism standards if adding any dashboard UI visualization for the Queue (using `backdrop-filter: blur(20px) saturate(200%)`).
