# Architecting KAIROS Orchestrator State Machine

## Problem Statement
The central KAIROS orchestrator needs a robust state machine to track the lifecycle of agent tasks, handle complex feature decompositions, and ensure no deadlocks occur during execution across the swarm.

## Research Report
- **Goal:** Design a distributed state machine for KAIROS task orchestration.
- **Context:**
  - KAIROS acts as the central brain, decomposing large requests into a sequence of smaller tasks.
  - The state machine must track these parent-child relationships and manage transitions (e.g., waiting for all sub-tasks to complete before marking the parent task as done).
  - Must be durable (backed by DB) and handle concurrent updates safely.
- **Key Requirements:**
  1.  **State Definitions:** Clear states (e.g., `RECEIVED`, `DECOMPOSING`, `EXECUTING_SUBTASKS`, `VERIFYING`, `COMPLETED`, `FAILED`).
  2.  **Transition Logic:** Rules for moving between states, including retry mechanisms and failure handling.
  3.  **Concurrency Control:** Preventing race conditions when multiple workers update sub-task statuses simultaneously.

## Design Doc
### State Machine Design
Create a `TaskStateMachine` component in `srcs/server/orchestration/state_machine.go`.

**States:**
- `PENDING`: Initial state.
- `DECOMPOSING`: KAIROS is breaking the task into sub-tasks.
- `EXECUTING`: Sub-tasks are queued and being processed by agents.
- `VERIFYING`: All sub-tasks complete; verifying the overall result.
- `DONE`: Successfully completed.
- `FAILED`: Terminal failure state.

**Data Model Enhancements (Shared Task List):**
Update the `ohc_tasks` table to include parent-child relationships:
- `parent_task_id` (TEXT, Nullable, foreign key to `ohc_tasks(id)`)
- `workflow_state` (JSON/TEXT, to store intermediate state data during transitions)

### Transition Logic
The state machine will expose a method `ProcessEvent(ctx, taskID, event)`.
Example Events: `SubTaskCompleted`, `SubTaskFailed`, `DecompositionComplete`.

When a `SubTaskCompleted` event arrives:
1.  Transaction starts.
2.  Lock the parent task row (`SELECT FOR UPDATE`).
3.  Check if all child tasks (where `parent_task_id = parentTask.id`) are `DONE`.
4.  If yes, update parent state to `VERIFYING` or `DONE`.
5.  Transaction commits.
