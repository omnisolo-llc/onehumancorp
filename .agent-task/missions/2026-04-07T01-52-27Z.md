# Agent Execution State Transition Latency Telemetry

**Priority:** P1
**Estimated Scope:** Medium

## Problem Statement
While OHC Hybrid Architecture (OHC-HA) currently exposes broad metrics like `ohc_task_processing_latency_seconds` and `ohc_task_queue_length`, we lack granular visibility into the exact duration an agent spends in discrete state transitions (e.g., `PENDING` -> `RUNNING` vs `RUNNING` -> `COMPLETED`). This observability gap makes it difficult to definitively identify if delays are caused by initial dispatch queuing (Wait Time) or by the actual LLM execution (Execution Time), which limits our ability to surgically optimize bottleneck workflows in both Cloud-Native and Standalone modes.

## Research Report
An analysis of `TELEMETRY_REPORT.md` and `OBSERVABILITY_AUDIT_REPORT.md` highlights that different deployment modes experience distinct latency profiles:
- **Cloud-Native Mode:** Latency is typically dominated by external network requests to LLM providers during the `RUNNING` state.
- **Standalone Mode:** Latency is heavily influenced by local SQLite I/O limits during task dispatch, elongating the `PENDING` -> `RUNNING` transition time.

To effectively self-correct and autoscale, the Swarm needs a high-fidelity histogram metric that captures latency per state transition, rather than just the overall lifecycle duration.

### Comparative Table: Current vs Proposed Telemetry
| Metric Capability | Current State | Proposed State |
| --- | --- | --- |
| Overall Task Latency | `ohc_task_processing_latency_seconds` | Maintained |
| Wait Time (PENDING -> RUNNING) | Invisible | `ohc_agent_transition_latency_seconds` (transition="pending_to_running") |
| Execution Time (RUNNING -> COMPLETED) | Invisible | `ohc_agent_transition_latency_seconds` (transition="running_to_completed") |

## Design Doc
1. **OpenTelemetry Instrumentation Update:**
   - In `srcs/server/telemetry/telemetry.go`, introduce a new Float64Histogram `ohc_agent_transition_latency_seconds`.
   - Implement `RecordAgentTransitionLatency(ctx context.Context, transitionType string, latencyMS float64)` to log the timing of specific state changes.
2. **Backend Logic Hooks:**
   - Update `srcs/server/orchestration/sip.go` or the relevant `Shared Task List` component where agent state transitions occur. Calculate the duration from the previous state timestamp and emit the metric.
3. **Grafana Dashboard Panel:**
   - Add a new timeseries panel in `deploy/docker/grafana/provisioning/dashboards/hybrid-telemetry.json` titled "Agent State Transition Latency" charting the P95 duration grouped by `transition` type.
