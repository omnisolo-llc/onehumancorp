# Architecting Sub-Agent Queue and Delegation

## Problem Statement
The KAIROS Orchestrator needs a reliable mechanism to spawn and manage isolated sub-agents in a production environment. When a high-level task is decomposed, the resulting sub-tasks must be queued, distributed to available agents, tracked for completion, and retried upon failure.

## Research Report
- **Goal:** Design the scalable background queuing logic for orchestrating sub-agents.
- **Context:**
  - Must operate robustly in Cloud Mode (high concurrency, multi-tenant) and gracefully degrade in Standalone Mode.
  - Needs to track the lifecycle of a sub-task (Queued -> Processing -> Completed/Failed).
- **Key Components:**
  1.  **Queue System:** A distributed queue (e.g., based on Redis Streams/Lists for Cloud, or a simple database-backed queue/in-memory queue for Standalone).
  2.  **Worker Pool:** A pool of agent workers listening to the queue.
  3.  **Lifecycle Management:** Tracking task timeouts, retries, and reporting results back to the parent orchestrator task.

## Design Doc
### Sub-Agent Queue Architecture
We will introduce a `SubAgentQueue` interface in `srcs/server/orchestration/queue.go`.

```go
type SubTask struct {
    ID string
    ParentTaskID string
    Payload []byte
    Priority int
    MaxRetries int
}

type SubAgentQueue interface {
    Enqueue(ctx context.Context, task SubTask) error
    Dequeue(ctx context.Context, agentIDs []string) (*SubTask, error) // agentIDs for routing if necessary
    Acknowledge(ctx context.Context, taskID string, success bool, result []byte) error
}
```

### Implementations
1.  **RedisQueue (Cloud):** Uses Redis Streams (`XADD`, `XREADGROUP`, `XACK`). This provides robust consumer groups, guaranteeing a task is processed by exactly one worker and enabling easy retries via `XPENDING`.
2.  **DBQueue (Standalone):** Uses a dedicated database table (`ohc_sub_tasks`) as a queue. `Dequeue` uses a transaction with `SELECT ... FOR UPDATE SKIP LOCKED` (in Postgres) or an atomic update (in SQLite).

### Integration with State Machine
When KAIROS decomposes a task, it inserts the parent task into the Shared Task List, then enqueues multiple `SubTask`s into the `SubAgentQueue`. Workers dequeue these tasks, process them, and `Acknowledge`. The parent task's state machine monitors the completion of all child tasks before transitioning to `DONE`.
