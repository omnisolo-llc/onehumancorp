# Title: Implement Per-Tenant Token Usage Forecasting

## Problem Statement
In Cloud-Native mode, there are gaps in detailed per-tenant token usage forecasting. While high metric coverage exists with OpenTelemetry/Prometheus, detailed forecasting per tenant is missing, hindering effective cost and resource management.

## Research Report
According to the docs/research/TELEMETRY_REPORT.md, the Cloud-Native mode architecture (Multi-tenant, Kubernetes, PostgreSQL/Redis) has high throughput and comprehensive Prometheus/Grafana coverage. However, the observability gap analysis explicitly notes: "However, there are gaps in detailed per-tenant token usage forecasting." Addressing this gap is necessary to provide better insights into token burn rates and forecast future usage accurately per organization.

## Design Doc
1. **Metric Definition**: Define a new OpenTelemetry metric in `srcs/server/telemetry/telemetry.go` for token usage forecasting (e.g., an UpDownCounter or Gauge) that includes `organization_id` as an attribute.
2. **Data Aggregation**: Implement a service or periodic job that aggregates historical token usage data per tenant to calculate forecasting metrics.
3. **API Endpoint**: If necessary, expose this forecasting data via an authenticated endpoint (e.g., `/api/v1/telemetry/forecast`) allowing the dashboard to consume it.

## Implementation Prompt
Hello Implementer, please execute the following:
1. In `srcs/server/telemetry/telemetry.go`, introduce a forecasting metric that tracks projected token usage, ensuring it uses the `organization_id` attribute.
2. Implement the background calculation logic that analyzes recent token usage rates and updates the forecasting metric periodically.
3. Ensure appropriate OpenTelemetry and Prometheus wrappers are applied.
4. Write unit tests for the forecasting logic and verify them with `bazelisk test //...`.
