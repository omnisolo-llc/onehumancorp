# Architecting the Teammate Mesh APIs

## Problem Statement
The OHC Swarm requires a highly available realtime communication layer (the "Teammate Mesh") to coordinate agents efficiently without deadlocks. The Shared Task List handles state persistence, but agents need immediate awareness of task delegations, lock availability, and peer status updates, especially in Cloud-Native (multi-tenant) environments.

## Research Report
- **Goal:** Design the Realtime Teammate Mesh APIs for agent coordination.
- **Context:** Must support both Cloud (Redis Pub/Sub or gRPC) and Standalone (in-memory bus or local SQLite events).
- **Key Requirements:**
    1.  **Publish/Subscribe Semantics:** Agents need to subscribe to topics (e.g., `tenant:123:tasks`, `agent:456:messages`).
    2.  **Distributed Locking (Git-Lock Coordination):** Agents need to acquire leases on specific resources (like a task or a file) to ensure exclusive access and prevent race conditions during distributed execution.
    3.  **Presence/Heartbeat:** Agents must broadcast their status (e.g., IDLE, WORKING, FAULT) so the orchestrator can reassign tasks if an agent dies.

## Design Doc
### Realtime Teammate Mesh Interface
Define an interface in `srcs/server/orchestration/mesh.go`:

```go
type TeammateMesh interface {
    // PubSub
    Publish(ctx context.Context, topic string, payload []byte) error
    Subscribe(ctx context.Context, topic string, handler func(msg []byte)) (Subscription, error)

    // Distributed Lock
    AcquireLock(ctx context.Context, key string, ttl time.Duration) (bool, error)
    ReleaseLock(ctx context.Context, key string) error

    // Presence
    RegisterPresence(ctx context.Context, agentID string, status string) error
    GetActiveAgents(ctx context.Context) ([]AgentPresence, error)
}
```

### Implementations
1.  **RedisMesh (Cloud Mode):** Uses go-redis. `Publish`/`Subscribe` map directly to Redis Pub/Sub. `AcquireLock` uses SET NX PX. `RegisterPresence` uses Redis Hash or sorted sets with TTLs.
2.  **LocalMesh (Standalone Mode):** Uses Go channels and `sync.RWMutex` for Pub/Sub. Uses standard memory locks for `AcquireLock`.

### Integration with Sub-Agent Queue
When KAIROS delegates a sub-task, it uses the Teammate Mesh to publish an event (`tasks:new`). Idle agents listening on the mesh attempt to `AcquireLock` on the task ID in the database. The winner proceeds.

## Implementation Prompt
**Title:** Implement Teammate Mesh API and Providers

**Instructions:**
1.  **Interface Definition:** Create `srcs/server/orchestration/mesh/mesh.go` defining the `TeammateMesh` interface.
2.  **Redis Provider:** Create `srcs/server/orchestration/mesh/redis_mesh.go` implementing the interface using `github.com/redis/go-redis/v9`. Ensure proper connection handling and error recovery.
3.  **Local Provider:** Create `srcs/server/orchestration/mesh/local_mesh.go` implementing an in-memory version for Standalone mode.
4.  **Wiring:** In `srcs/server/main.go` (or wherever orchestration is initialized), inject the correct `TeammateMesh` provider based on the `DATABASE_URL` or `OHC_MULTITENANT` configuration.
5.  **Testing:** Write unit tests for both providers in `srcs/server/orchestration/mesh/mesh_test.go`. Mock Redis where appropriate or use a mini-redis package for integration testing.

Ensure all implementations are robust and handle context cancellations cleanly.
