# Architecture: Realtime Teammate Mesh APIs & Shared Task List

## Problem Statement
One Human Corp's Swarm Intelligence Protocol currently lacks a durable, distributed state machine for cross-agent task handoffs and dependency tracking. In Cloud mode, agents need high-throughput distributed queues and pub/sub. In Standalone mode, they require local SQLite-based concurrency management to prevent I/O bottlenecks. Without a unified abstraction, agent coordination either deadlocks locally or loses state in the cloud. We need the "Teammate Mesh Architecture" designed for OHC-HA.

## Research Report

### Competitive Analysis & State of the Art
| System | Strengths | Weaknesses | OHC Fit |
|---|---|---|---|
| Temporal / Cadence | Durable state, complex DAGs | Extreme operational overhead, heavyweight Java/Go workers | ❌ Too heavy for Standalone Mode |
| Redis Pub/Sub + BullMQ | High throughput, standard Cloud pattern | Fails without Redis, requires separate node processes | ⚠️ Good for Cloud, breaks Standalone |
| **OHC Hybrid Mesh** | Degrades gracefully to SQLite, pure Go | Requires custom polling/locking implementation | ✅ Ideal. Fits OHC-HA perfectly. |

## Design Doc

### 1. Database Schema (`shared_tasks`)
To maintain the "Hybrid Consistency" mandate, this schema must work identically in PostgreSQL and SQLite.

```sql
CREATE TABLE shared_tasks (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    status TEXT NOT NULL DEFAULT 'PENDING', -- PENDING, IN_PROGRESS, DONE, BLOCKED
    assigned_agent_id TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

### 2. Teammate Mesh API Contract
We will establish a unified Go interface for the Teammate Mesh, allowing seamless swapping between Redis and local Go channels/SQLite.

```go
package orchestration

import "context"

type TeammateMesh interface {
    // Broadcasts a task update to the swarm
    BroadcastTask(ctx context.Context, task Task) error
    // Subscribes to the 'mesh:tasks' channel
    SubscribeTasks(ctx context.Context) (<-chan Task, error)
}
```

### 3. Payload Specification
Mesh messages must use exact payload keys as specified in platform memory: `agent_id`, `action`, and `status`.

```json
{
  "agent_id": "agent-123",
  "action": "PICK_UP_TASK",
  "status": "IN_PROGRESS",
  "task_id": "task-456"
}
```

## Implementation Prompt

**Role:** Implementer (Go Backend)
**Objective:** Implement the Teammate Mesh and `shared_tasks` state machine.

**Instructions:**
1. **Schema:** Add the `shared_tasks` table to `srcs/server/db/migrations/`. Ensure standard `ADD COLUMN` is used (no `IF NOT EXISTS` for SQLite compatibility).
2. **Interface:** Create `TeammateMesh` in `srcs/server/orchestration/mesh.go`.
3. **Cloud Implementation:** Implement `RedisTeammateMesh` using `rueidis`. Parse the connection string via `rueidis.ParseURL(redisURL)`. Publish to the `mesh:tasks` channel.
4. **Standalone Implementation:** Implement `LocalTeammateMesh`. Instead of Redis, persist directly to the `shared_tasks` table in SQLite and use local Go channels for broadcasting.
5. **UI Hub:** Update `Hub.PublishTaskBroadcast` to send `{ "agent_id": ..., "action": ..., "status": ... }`.
6. **Tests:** Write unit tests in `srcs/server/orchestration/mesh_test.go`. Use `t.Setenv("DATABASE_URL", "sqlite://file::memory:?mode=memory")` without `cache=shared` for local SQLite testing. Explicitly create the schema in the test setup. Remember to avoid reassignment of sync primitives in tests (use a reset helper function).

**Acceptance Criteria:**
* `bazelisk test //srcs/server/...` passes 100%.
* Both implementations satisfy the interface and fallback gracefully.
* Code adheres to "Skeptical Memory" verification protocols.
