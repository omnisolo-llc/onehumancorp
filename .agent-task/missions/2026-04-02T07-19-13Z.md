# Implement Token Burn Rate Forecasting & SQLite Concurrency Throttling

## Problem Statement
The OHC Hybrid Architecture (OHC-HA) is experiencing divergent performance bottlenecks across its deployment modes.
In Cloud-Native mode, there's a lack of proactive Token Burn Rate Forecasting, leaving tenants blind to sudden budget consumption spikes.
In Standalone Desktop mode, high-concurrency swarm interactions with the local SQLite `swarm.db` are causing rapid "database is locked" errors, crashing the local agent swarm during burst workloads.

## Research Report
Based on a recent Observability Audit of the Hybrid Architecture, the primary inefficiency in Standalone Mode is SQLite database lock contention. SQLite struggles with highly parallel writes when the local swarm delegates tasks aggressively.
Additionally, while raw token usage is tracked via the `ohc_token_usage_total` metric, there is no system projecting future burn rates based on moving averages. This creates a critical observability gap.
*See the full Observability Audit Report at `OBSERVABILITY_AUDIT_REPORT.md` for complete findings.*

## Design Doc
### 1. Token Burn Rate Forecasting Engine
- **Component**: Backend daemon in Orchestration Hub.
- **Functionality**: Calculate moving average burn rate using `ohc_token_usage_total` and emit predictive cost alerts.
- **Observability**: Expose the metric to Prometheus and add a Grafana dashboard panel to `deploy/docker/grafana/provisioning/dashboards/hybrid-telemetry.json`.
- **Architecture**:

### 2. Standalone SQLite Concurrency Throttling
- **Component**: `DelegateMission` function in the OHC Go Backend.
- **Functionality**: Implement a dynamic concurrency limiter (semaphore).
- **Condition**: Only active when `OHC_STANDALONE=true` (do NOT check `OHC_MULTITENANT=false` directly for this).
- **Goal**: Strictly throttle parallel agent writes to SQLite, trading raw throughput for zero-error stability to prevent `database is locked` bottlenecks.
