# Mission: Elastic Swarm Bursting

## Problem Statement
When Standalone OHC clients (running on local SQLite and limited compute like Apple Silicon) encounter intensive tasks, they currently lack the ability to seamlessly offload ("burst") these tasks to the OHC Cloud-Native API. Replit and Claude Code are constrained to their respective execution environments. This capability is uniquely suited for OHC's Hybrid Architecture, enabling zero-latency Local-Private RAG to scale horizontally in the cloud without exposing proprietary local code.

## Research Report
The Market Audit (docs/research/hybrid-agentic-os-audit.md) identified "Elastic Swarm Bursting" as a critical competitive advantage over Claude Code, OpenClaw, and Replit Agent.
Currently, `SIPDB` has a `BurstMission` method that updates the status to `'BURSTING'` and updates the DB. However, the `agent_missions` synchronization loop needs to securely hand off these missions to the OHC Cloud-Native API over SPIFFE/SPIRE authenticated gRPC or HTTP endpoints.
The `statesyncmcp` provider (`srcs/server/tools/statesyncmcp/provider.go`) already injects the `SPIFFE_IDENTITY_TOKEN` into sync requests, demonstrating how zero-trust identity is implemented locally. The `SyncUp` loop only queries `synced_to_cloud = false`, we need the underlying orchestrator synchronization mechanism to recognize the `'BURSTING'` status and correctly proxy the payload and state.

## Design Doc
1. **API Endpoints**: Ensure the OHC Cloud-Native API handles inbound `BURSTING` tasks from local SQLite instances securely. Validate SPIFFE tokens natively.
2. **State Transition**: Local SQLite sets status to `BURSTING` using `BurstMission`. The local `sync_daemon.go` (or `sync_missions` logic) detects `BURSTING` tasks, packages the `agent_missions` payload, and sends it to the Cloud API (via SPIFFE-authenticated requests).
3. **Cloud Execution**: The Cloud Postgres SIPDB receives the burst payload, verifies the SPIFFE ID, executes the mission using cloud resources, and transitions the cloud state to `COMPLETED` or `FAILED`.
4. **State Sync Down**: The Standalone host periodically polls or syncs down from the Cloud API using `statesyncmcp` or `autodream_sync`, retrieving the updated payload and status.
5. **Conflict Resolution**: The local client remains the source of truth for conflict resolution. Ensure `IsSQLite()` is used appropriately instead of Postgres-specific syntax when updating local status.
