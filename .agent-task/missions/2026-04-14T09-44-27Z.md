# Mission: Implement KAIROS Hybrid Agentic OS Foundation

**Title:** Hybrid Teammate Mesh, AutoDream Vector Pipeline, and KAIROS State Machine Implementation

**Problem Statement:**
The OHC Swarm requires robust, distributed infrastructure to coordinate, track dependencies, and manage semantic memory across cloud-native (PostgreSQL/Redis) and standalone (SQLite) operating modes.

**Research Report:**
- KAIROS Orchestration demands a three-pillared foundation: the Shared Task List (State Machine), Teammate Mesh (Realtime Pub/Sub), and AutoDream (Memory Consolidation).
- The system must seamlessly transition between Postgres/Redis for scalable cloud environments and SQLite for local deployments.
- Teammate Mesh coordination relies on `CentrifugeNode` and requires tracking deterministic task transitions.
- AutoDream requires `pgvector` to avoid context window overflows when processing massive ephemeral session histories.

**Design Doc:**
### 1. Distributed State Machine (Shared Task List)
- **DB Schema (`state_machine_transitions`):**
  - `id TEXT PRIMARY KEY`
  - `entity_id TEXT NOT NULL`
  - `entity_type TEXT NOT NULL`
  - `from_state TEXT NOT NULL`
  - `to_state TEXT NOT NULL`
  - `agent_id TEXT`
  - `reason TEXT`
  - `occurred_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`
- **Concurrency:** Use `FOR UPDATE SKIP LOCKED` (Postgres) or application-level locks (SQLite) when dequeuing tasks.
- **Sub-Agent Queue (`sub_agent_jobs`):** Enqueue delegated jobs, handle `max_attempts` retries.

### 2. Teammate Mesh API Contracts
- **Channels:** `mesh:tasks`, `mesh:coordination`, `mesh:ultraplan`.
- **Transport Interfaces:** Implement `MeshTransport` supporting both `RedisMeshTransport` (rueidis) and `MemoryMeshTransport` (fallback).
- **Hub:** Use `CentrifugeNode` to publish `StateTransitionEvent` upon successful updates to the state machine.

### 3. AutoDream Data Pipeline
- **DB Schema (`autodream_memories`):**
  - `id TEXT PRIMARY KEY`
  - `organization_id TEXT NOT NULL`
  - `agent_id TEXT`
  - `content TEXT NOT NULL`
  - `embedding vector(1536)`
  - `source_type TEXT NOT NULL`
  - `created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`
- **Vector Logic:** `pgvector` (Cloud) vs `JSON blob` fallbacks (Standalone).

**Implementation Prompt:**
Implementer, follow these strict execution requirements:
1. **Database Setup:** Create a new sequential SQL migration file (e.g., `052_kairos_foundation.sql`) in `srcs/server/db/migrations/` containing the schemas for `state_machine_transitions`, `sub_agent_jobs`, and `autodream_memories`.
2. **Embeddings:** Ensure `CREATE EXTENSION IF NOT EXISTS vector;` is included for PostgreSQL, and add logic to gracefully handle SQLite fallback in `srcs/server/db/database.go` or the repository layer.
3. **Build Context:** Update `srcs/server/db/BUILD.bazel` to include your new migration file in the `embedsrcs` list.
4. **Teammate Mesh:** Implement the `MeshTransport` interface in the `srcs/server/orchestration/` package. Initialize the Centrifuge hub and bind the `StateTransitionEvent` broadcast logic.
5. **Observability:** Embed OpenTelemetry traces/spans for all database transactions and queue pop operations. Ensure all `err` variables are checked sequentially using `if err != nil`.
6. **Verification:** Write test cases for the KAIROS foundation. Use `os.Setenv("DATABASE_URL", "sqlite://:memory:")`, `db.New(ctx)`, and `database.RunMigrations(ctx)` for SQLite in-memory isolation. Target testing specifically at `//srcs/server/orchestration:orchestration_test`.
