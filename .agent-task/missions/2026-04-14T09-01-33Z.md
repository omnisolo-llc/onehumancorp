<h1>Mission: Implement KAIROS Hybrid Agentic OS Foundation</h1>

<b>Title:</b> Hybrid Teammate Mesh, AutoDream Vector Pipeline, and KAIROS State Machine Implementation
<b>Problem Statement:</b> The OHC Swarm requires robust, distributed infrastructure to coordinate, track dependencies, and manage semantic memory across cloud-native (PostgreSQL/Redis) and standalone (SQLite) operating modes.
<b>Priority:</b> P0
<b>Estimated Scope:</b> Large

<h2>Research Report</h2>
<b>Findings:</b>
1. KAIROS Orchestration demands a three-pillared foundation: the Shared Task List (State Machine), Teammate Mesh (Realtime Pub/Sub), and AutoDream (Memory Consolidation).
2. The system must seamlessly transition between Postgres/Redis for scalable cloud environments (`OHC_MULTITENANT=true`) and SQLite for local deployments (`OHC_STANDALONE=true` or missing `DATABASE_URL`).
3. Teammate Mesh coordination relies on `CentrifugeNode` and requires tracking deterministic task transitions.
4. AutoDream requires `pgvector` to avoid context window overflows when processing massive ephemeral session histories.

<h2>Design Doc</h2>
<b>1. Distributed State Machine (Shared Task List)</b>
- <b>DB Schema (`state_machine_transitions`):</b>
  - `id TEXT PRIMARY KEY`
  - `entity_id TEXT NOT NULL`
  - `entity_type TEXT NOT NULL`
  - `from_state TEXT NOT NULL`
  - `to_state TEXT NOT NULL`
  - `agent_id TEXT`
  - `reason TEXT`
  - `occurred_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`
- <b>Concurrency:</b> Use `FOR UPDATE SKIP LOCKED` (Postgres) or application-level locks (SQLite) when dequeuing tasks.
- <b>Sub-Agent Queue (`sub_agent_jobs`):</b> Enqueue delegated jobs, handle `max_attempts` retries.

<b>2. Teammate Mesh API Contracts</b>
- <b>Channels:</b> `mesh:tasks`, `mesh:coordination`, `mesh:ultraplan`.
- <b>Transport Interfaces:</b> Implement `MeshTransport` supporting both `RedisMeshTransport` (rueidis) and `MemoryMeshTransport` (fallback).
- <b>Hub:</b> Use `CentrifugeNode` to publish `StateTransitionEvent` upon successful updates to the state machine.

<b>3. AutoDream Data Pipeline</b>
- <b>DB Schema (`autodream_memories`):</b>
  - `id TEXT PRIMARY KEY`
  - `organization_id TEXT NOT NULL`
  - `agent_id TEXT`
  - `content TEXT NOT NULL`
  - `embedding vector(1536)`
  - `source_type TEXT NOT NULL`
  - `created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`
- <b>Vector Logic:</b> `pgvector` (Cloud) vs `JSON blob` fallbacks (Standalone).

<h2>Implementation Prompt</h2>
Implementer, follow these strict execution requirements:
1. <b>Database Setup:</b> Create a new sequential SQL migration file (e.g., `052_kairos_foundation.sql`) in `srcs/server/db/migrations/` containing the schemas for `state_machine_transitions`, `sub_agent_jobs`, and `autodream_memories`.
2. <b>Embeddings:</b> Ensure `CREATE EXTENSION IF NOT EXISTS vector;` is included for PostgreSQL, and add logic to gracefully handle SQLite fallback in `srcs/server/db/database.go` or the repository layer.
3. <b>Build Context:</b> Update `srcs/server/db/BUILD.bazel` to include your new migration file in the `embedsrcs` list.
4. <b>Teammate Mesh:</b> Implement the `MeshTransport` interface in the `srcs/server/orchestration/` package. Initialize the Centrifuge hub and bind the `StateTransitionEvent` broadcast logic.
5. <b>Observability:</b> Embed OpenTelemetry traces/spans for all database transactions and queue pop operations. Ensure all `err` variables are checked sequentially using `if err != nil`.
6. <b>Verification:</b> Write test cases for the KAIROS foundation. Use `os.Setenv("DATABASE_URL", "sqlite://:memory:")`, `db.New(ctx)`, and `database.RunMigrations(ctx)` for SQLite in-memory isolation. Target testing specifically at `//srcs/server/orchestration:orchestration_test`.
