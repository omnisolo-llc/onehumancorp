# 📊 Mission: Implement Telemetry for SQLite Database Lock Contention

## Problem Statement
In Standalone Desktop Mode, OHC operates with a local SQLite database (`swarm.db`) to track agent states and orchestration tasks. Under high Swarm concurrency, the `DelegateMission` throughput is constrained by SQLite's single-writer limitation, leading to "database is locked" (`SQLITE_BUSY`) errors. While we have introduced a synchronous degradation fallback in `DelegateMission`, we currently have **zero telemetry visibility** into how frequently these locks occur, how long transactions are delayed due to lock contention, and how many exponential backoff retries are exhausted. Without this observability, we cannot effectively tune our Standalone agent workforce limits or verify if SQLite write optimizations are successful.

### Hybrid Architecture Bottleneck Analysis

Our Hybrid Agentic OS behaves fundamentally differently depending on the deployment mode. In Cloud-Native Mode, PostgreSQL efficiently multiplexes write transactions. However, in Standalone Desktop Mode, the SQLite lock mechanism becomes the primary I/O bottleneck.

| Metric | Cloud-Native Mode (PostgreSQL) | Standalone Mode (SQLite) |
| --- | --- | --- |
| Write Concurrency | High (Row-level locking) | Low (Database-level locking) |
| Contention Behavior | Wait states tracked via `pg_stat_activity` | Fails with `SQLITE_BUSY` or blocks |
| Resolution Strategy | Connection pooling & scaling | Application-level retry & backoff |
| **Current Visibility** | High | **Critical Gap** |

By instrumenting `SQLITE_BUSY` errors and retry backoffs, we can accurately measure the cost of our Swarm Intelligence Protocol (OHC-SIP) when running in constrained environments.

## Design Doc

### 1. New Telemetry Metrics in `srcs/server/telemetry/telemetry.go`
We will introduce two new OpenTelemetry counters:
*   `sqlite_lock_contention_total`: An `Int64Counter` tracking the number of times a `SQLITE_BUSY` error or database lock timeout is encountered.
*   `sqlite_retry_exhausted_total`: An `Int64Counter` tracking when an operation fundamentally fails after exhausting its maximum backoff retries.

### 2. Instrumentation in the Data Access Layer
We must wrap the database execution logic (specifically in `srcs/server/db/provider.go` or within the `orchestration` persistence layer like `tasks.go` and `task_orchestrator.go`) with telemetry hooks.
Functions performing writes (e.g., `Exec`, `Begin`, `Commit`) in the SQLite provider context must be updated to inspect errors for "database is locked" or `SQLITE_BUSY` strings and increment the `sqlite_lock_contention_total` metric.

### 3. Grafana Dashboard Update
Update `deploy/docker/grafana/provisioning/dashboards/hybrid-telemetry.json` and `ohc-hybrid.json` to include a new panel: "Standalone SQLite Contention Rate", visualizing `sum(rate(sqlite_lock_contention_total[5m]))`.
