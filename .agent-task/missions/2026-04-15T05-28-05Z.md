# Title: Implement Offline-Capable Action Queue for Hybrid OS

## Problem Statement
While OHC currently features a "Hybrid MCP RAG Protocol" that handles synchronizing local context vectors to cloud PostgreSQL, and a "Hybrid CRDT Sync MCP" for merging state vectors, it lacks an **Offline-Capable Action Queue**. When a local Standalone Desktop agent needs to issue API calls to cloud services (like sending an email or triggering a remote build) but the machine is offline, those requests either fail or block. Claude Code operates entirely locally but doesn't handle cloud escalations offline, while Replit Agent fails completely without a connection. We need the "Action Queue" layer of our OS to support storing intents locally and transparently draining them when network parity is restored.

## Research Report
**Competitive Analysis:**
- **Claude Code**: Fails if an API call is made offline.
- **Replit Agent**: Entirely cloud-bound; cannot function offline.
- **OHC (Current)**: Syncs state (CRDT) and knowledge (RAG) offline-to-cloud, but lacks a mechanism to queue actionable external API intents (e.g., webhook fires, email sends, 3rd party tool calls) during offline operation.

**Findings:**
A true "Hybrid Agentic OS" must ensure that high-level operational commands (actions) issued by local agents are durably queued and executed once connectivity is restored. This bridges the remaining gap for seamless standalone-to-cloud resilience.

## Design Doc
**Architecture:**
- Create an `ActionQueue` interface that intercepts external/cloud action requests from agents in Standalone mode.
- In Standalone mode (SQLite), it writes an `intent` record to a local queue table.
- A background worker (`ActionDrainWorker`) monitors network connectivity and, upon reconnect, drains the local queue by sending the actions to the Cloud API (`POST /api/v1/queue/drain`).
- The Cloud backend processes these intents idempotently and returns the resulting state changes.

**DB Schema Changes (SQLite Local):**
```sql
CREATE TABLE IF NOT EXISTS offline_action_queue (
    id TEXT PRIMARY KEY,
    agent_id TEXT NOT NULL,
    action_type TEXT NOT NULL,
    payload JSON,
    status TEXT DEFAULT 'QUEUED',
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

**API Contracts:**
- `POST /api/v1/queue/drain`: Cloud endpoint to accept an array of offline actions and process them.

## Implementation Prompt
**Implement the Offline-Capable Action Queue for Hybrid OS.**

1.  **Database Migration (Local SQLite):**
    *   Create a new migration file in `srcs/server/db/migrations/` (e.g., `016_offline_action_queue.sql`) to define the `offline_action_queue` table as specified in the Design Doc. Do not forget to update `srcs/server/db/BUILD.bazel`.

2.  **API Endpoint & Controller:**
    *   Implement `POST /api/v1/queue/drain` in `srcs/server/dashboard/` to receive queued actions.
    *   It should accept a JSON array of `OfflineAction` structs, iterate over them, and mark them as processed in the cloud database (you may need to mock the processing logic for now or store them in a cloud equivalent table).

3.  **Local Queue Manager & Background Drainer:**
    *   Implement an `ActionQueue` manager in `srcs/server/orchestration/` that provides a method to `EnqueueAction`.
    *   Implement a background drainer (e.g., in `srcs/server/main.go` or a new worker package) that periodically checks for connectivity (e.g., pinging a health endpoint) and calls `/api/v1/queue/drain` with the queued items when online, then marks them `DRAINED` locally.

4.  **Tests:**
    *   Add Go tests to verify the local enqueueing mechanism and the cloud drain API handler.

Ensure all new Go files and dependencies are properly registered in their respective `BUILD.bazel` files.
