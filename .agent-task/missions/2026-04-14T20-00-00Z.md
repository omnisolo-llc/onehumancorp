# Problem Statement
Agents need a reliable and scalable mechanism to coordinate task assignment events without delay, while maintaining deadlock-free workflows. The existing Swarm architecture lacks an integrated system tying the real-time Teammate Mesh broadcasting with the Shared Task List state machine. Without this integration, human orchestrators and other sub-agents cannot monitor system state changes instantaneously, limiting the Swarm's autonomous orchestration capacity across both Cloud-Native and Standalone modes.

# Research Report
The KAIROS Orchestration relies heavily on two foundational pillars:
1. **Shared Task List (State Machine):** Uses `shared_tasks_decomposition` database schema. The lock acquisition requires PostgreSQL's `FOR UPDATE SKIP LOCKED` for robust cloud concurrency and explicit transactions in SQLite for standalone resilience.
2. **Teammate Mesh (Real-time Broadcasts):** Exposes `POST /api/mesh/v2/broadcast` via `srcs/server/dashboard/server.go`. Depending on the mode, this relies on a Redis `MeshBroker` (`rueidis`) or a local Go channels `MeshBroker`.

Currently, we have previously designed the database schema, but lack the Go implementations linking these systems securely.

# Design Doc
Refer to the architectural guidelines found in `docs/architecture/kairos_task_decomposition_design.md` and `docs/architecture/kairos_hybrid_os_orchestration_design.md`.
The implementation requires:
- `TaskStore` interface and `SharedTaskOrchestrator` in `srcs/server/orchestration/tasks_store.go` and `srcs/server/orchestration/tasks_db.go`.
- `MeshBroker` interface and `LocalMeshBroker`, `RedisMeshBroker`, and `HTTPHandler` implementations in `srcs/server/orchestration/mesh/`.
- Integrating `HTTPHandler` for `POST /api/mesh/v2/broadcast` endpoint in `srcs/server/dashboard/server.go`.
