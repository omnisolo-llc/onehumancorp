# Problem Statement
The KAIROS Orchestration deliberates and executes across four distinct phases (Phase 1 to Phase 4). However, our Prometheus metrics configuration in `deploy/docker/prometheus/prometheus-agent.yml` and `deploy/docker/prometheus/prometheus.yml` currently lacks scrape configs that specifically target or dynamically discover the ephemeral pods or local processes spawned during these phase executions. Without capturing metrics (like `ohc_deliberation_phase_duration_seconds_bucket`) specifically for these short-lived processes, our Full-Spectrum Observability requirement is violated, leaving the Hybrid OS blind to potential bottlenecks during orchestration.

# Research Report
Reviewing the current metrics configuration:
- `deploy/docker/prometheus/prometheus.yml` rigidly defines static targets `server:8080` and `ohc-core:18789`.
- `deploy/docker/prometheus/prometheus-agent.yml` hardcodes `localhost:8080`.
The KAIROS orchestration phases heavily utilize transient sub-agents and dynamically spawned Go routines or K8s jobs (as detailed in `docs/architecture/kairos_orchestrator.md` and `docs/architecture/kairos_task_decomposition_design.md`). Because Prometheus operates on a pull model, it misses metrics from these short-lived agents if they terminate before a scrape interval. Furthermore, the `ohc_deliberation_phase_duration_seconds_bucket` metric exists in our Grafana dashboards (`hybrid-telemetry.json`) but without the necessary pushgateway or dynamic service discovery, data will be lost.

# Design Doc
To address this observability gap in the Hybrid context (both Cloud-Native and Standalone):
1. **Cloud-Native Mode:** Introduce a Prometheus Pushgateway deployment in our helm charts and Docker Compose files to allow ephemeral KAIROS sub-agents to push their phase metrics before termination. Update `prometheus.yml` to scrape the Pushgateway.
2. **Standalone Mode:** In `prometheus-agent.yml`, configure remote write or local scraping to the Pushgateway running locally, or configure the standalone `ohc-core` process to buffer and expose these metrics on a dedicated endpoint (`:18790/metrics`) explicitly for KAIROS orchestration phases.
3. **Telemetry Bridge:** Implement a `PushMetrics` function in `srcs/server/telemetry/telemetry_bridge.go` that agents can call at the end of each deliberation phase.

# Implementation Prompt
Hello Implementer,

Please implement Pushgateway support for KAIROS Orchestration telemetry to ensure ephemeral sub-agents metrics are reliably captured.

1. **Update Prometheus Configs:** Add a Pushgateway scrape target to `deploy/docker/prometheus/prometheus.yml` (e.g., `pushgateway:9091`).
2. **Deploy Pushgateway:** Add the official Prometheus Pushgateway image to `deploy/docker-compose.yml` and create a corresponding Kubernetes deployment/service in `deploy/helm/ohc/templates/`.
3. **Enhance Telemetry Bridge:** In `srcs/server/telemetry/telemetry_bridge.go`, implement a `PushMetrics(ctx context.Context, jobName string)` function using the Prometheus `push` package (`github.com/prometheus/client_golang/prometheus/push`) to push accumulated metrics (specifically the deliberation phase durations) to the Pushgateway endpoint configured via an environment variable `PROMETHEUS_PUSHGATEWAY_URL`.
4. **Test:** Write unit tests for `PushMetrics` in `srcs/server/telemetry/telemetry_extra_test.go` and ensure all bazel tests pass (`bazelisk test //srcs/server/telemetry/...`).

Acceptance Criteria:
- Pushgateway is deployable via both docker-compose and Helm.
- Ephemeral agents can successfully push metrics to it without data loss.
