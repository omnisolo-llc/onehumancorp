# Shared Task List & Teammate Mesh Orchestration

## Problem Statement
The OHC Hybrid Agentic OS requires a robust, distributed state machine and task delegation system to seamlessly orchestrate complex, multi-agent workflows. As OHC agents decompose high-level features (KAIROS mode), they need a reliable, durable queue to pass tasks, manage dependencies, and coordinate in real-time across both Cloud-Native (Multi-tenant) and Standalone (Local) modes. Without a formalized shared task queue, complex feature deliveries risk deadlock, race conditions, or dropped tasks during cross-mode handoffs.

## Research Report
- **Competitive Landscape**: Orchestration systems like Temporal, BullMQ, and Celery provide strong durability but often lack native LLM-agent semantics (e.g., semantic task matching, AutoDream integration).
- **Current OHC State**: We have `swarm_tasks` and `shared_tasks` tables introduced in recent migrations (`008_swarm_tasks.sql`, `007_teammate_mesh_and_autodream.sql`), alongside basic Redis Pub/Sub capabilities via `github.com/redis/rueidis` in the Teammate Mesh.
- **Architectural Gaps**:
  1. The Teammate Mesh lacks a formalized state machine to manage task dependencies (e.g., Task B blocked by Task A).
  2. We need an abstraction layer (Sub-Agent Orchestrator) that seamlessly degrades from Redis-backed workers (Cloud) to local goroutine queues (Standalone).
  3. The AutoDream system needs to index completed tasks to continuously inject real-world context into the swarm's memory vector DB.

## Design Doc

### 1. Database Schema
Extend the existing `shared_tasks` / `swarm_tasks` schemas to support dependency tracking and semantic embeddings.

```sql
-- New Migrations (PostgreSQL, with SQLite fallbacks in db.go)
CREATE TABLE IF NOT EXISTS task_dependencies (
    task_id UUID NOT NULL,
    depends_on_task_id UUID NOT NULL,
    PRIMARY KEY (task_id, depends_on_task_id),
    FOREIGN KEY (task_id) REFERENCES shared_tasks(id) ON DELETE CASCADE,
    FOREIGN KEY (depends_on_task_id) REFERENCES shared_tasks(id) ON DELETE CASCADE
);

CREATE INDEX idx_task_deps_task ON task_dependencies(task_id);
CREATE INDEX idx_task_deps_depends ON task_dependencies(depends_on_task_id);
```

### 2. Teammate Mesh & State Machine (Go Backend)
- **Interface**: `TaskOrchestrator` in `srcs/server/orchestration/`
- **Cloud Mode**: Utilize `rueidis` Redis Distributed Locks (`.Nx().Px(...)`) for atomic task checkout. Use Redis Pub/Sub (`mesh:tasks:events`) for broadcasting state transitions (`PENDING` -> `IN_PROGRESS` -> `COMPLETED`).
- **Standalone Mode**: Use local `sync.Mutex` and `sync.Cond` for coordination. Persist directly to SQLite `shared_tasks`.
- **State Machine**:
  - `PENDING`: Task created, dependencies may be unresolved.
  - `READY`: All dependencies in `COMPLETED` state.
  - `IN_PROGRESS`: Agent acquired lock.
  - `COMPLETED`: Result submitted. Trigger AutoDream ingestion.
  - `BLOCKED`: Task blocked by external factors.
  - `FAILED`: Terminal failure.

### 3. Sub-Agent Queuing Logic
Implement a lightweight worker pool in Go that listens to the `TaskOrchestrator`.
- Agents subscribe to specific task capabilities (e.g., `IMPLEMENTER`, `DESIGNER`).
- Queue pushes `READY` tasks to available agents via the Mesh.

### 4. AutoDream Pipeline
When a task reaches `COMPLETED`, a background worker summarizes the task input/output using the `CachedMinimaxClient` and inserts the `VECTOR(1536)` embedding into `autodream_memories` (or `swarm_long_term_memory`), allowing the swarm to learn from past executions.

2. **Models**: Add Go struct models for `Task` and `TaskDependency` in `srcs/server/models/`.
3. **Orchestration Layer**:
   - Create `srcs/server/orchestration/task_queue.go`.
   - Implement `TaskOrchestrator` with methods: `EnqueueTask(ctx, task)`, `AcquireReadyTask(ctx, agentID, capabilities)`, `CompleteTask(ctx, taskID, result)`.
   - **Crucial**: Ensure atomicity using `rueidis` locks (`.Nx().Px(...)`) in Cloud mode and DB transactions/mutexes in Standalone mode. Use a single `Lock()` to prevent TOCTOU races.
4. **Mesh Integration**: In `CompleteTask`, broadcast a `TASK_COMPLETED` event via Redis Pub/Sub (`mesh:tasks`). In Standalone mode, signal a local event channel.
5. **AutoDream Hook**: In `CompleteTask`, trigger an asynchronous goroutine to generate a summary embedding via `CachedMinimaxClient` and insert it into `autodream_memories`.
6. **Tests**: Create `srcs/server/orchestration/task_queue_test.go`. Use `t.Setenv("DATABASE_URL", "sqlite://file::memory:?mode=memory")` for isolated in-memory testing. Write tests validating dependency resolution (Task B only becomes READY when Task A completes).

**Acceptance Criteria:**
- `TaskOrchestrator` passes all tests locally with >90% coverage for the new package.
- No memory leaks in background tracking maps (explicitly delete keys).
- Seamless fallback between Postgres/Redis and SQLite/Local channels.
