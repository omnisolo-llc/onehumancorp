# Title: Implement KAIROS Shared Task List and Teammate Mesh APIs

## Problem Statement
The OHC platform currently lacks the structural backend implementations to coordinate our agent swarm. We need the database tables for tracking distributed agent missions (Shared Task List), a Teammate Mesh API layer to support real-time agent coordination, and the foundational schemas for long-term "AutoDream" vector memory consolidation.

## Research Report
- Cloud-Native Mode (PostgreSQL) must use `FOR UPDATE SKIP LOCKED` to allow highly concurrent sub-agents to claim queue jobs safely.
- Standalone Desktop Mode (SQLite) must degrade gracefully and rely on application-level mutexes or simple isolated transactions, due to lack of `SKIP LOCKED`.
- The `Teammate Mesh` requires decoupled Pub/Sub. In the cloud, this is Redis. In SQLite standalone, it will fall back to an in-memory or polling table design.
- The `AutoDream` memories require pgvector in Postgres. For SQLite, we will store a serialized embedding cache.

## Design Doc

### 1. Database Architecture: Shared Task List
Table `shared_tasks`:
- `id` (UUID/String)
- `organization_id` (UUID/String) - Tenant isolation
- `parent_plan_id` (String) - KAIROS breakdown tracking
- `title` (String), `description` (Text)
- `status` (Enum: PENDING, IN_PROGRESS, REVIEW, COMPLETED, FAILED)
- `agent_id` (String) - Assigned agent
- `dependencies` (JSONB) - For DAG execution
- `created_at`, `updated_at`

### 2. Microservice API: Teammate Mesh (Hub)
- The Mesh orchestrator must abstract the transport.
- Interfaces: `ClaimTask(ctx, agentID)`, `CompleteTask(ctx, taskID)`
- The task assignment logic must verify `status = 'PENDING'` and atomically update to `ASSIGNED` with the caller's agent ID.

### 3. Data Pipelines: AutoDream
- Table `autodream_memories`:
  - `id`, `organization_id`, `vector_embedding` (pgvector 1536 dims), `content` (Text), `created_at`.
- Agent memories are persisted into the Swarm Intelligence Protocol (OHC-SIP).

## Implementation Prompt
Please implement the data access layer for claiming tasks in `srcs/server/orchestration/tasks_db.go`.
1. Create a method `ClaimTask(ctx context.Context, agentID string) (*SharedTaskDB, error)` on `TaskOrchestrator`.
2. Determine if the provider is SQLite or Postgres.
3. For Postgres, use the query `SELECT * FROM shared_tasks WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED` and update to 'ASSIGNED'.
4. For SQLite, use a global application mutex and a standard SELECT/UPDATE transaction.
5. Create unit tests in `srcs/server/orchestration/tasks_db_test.go` confirming both SQLite and Postgres paths.
