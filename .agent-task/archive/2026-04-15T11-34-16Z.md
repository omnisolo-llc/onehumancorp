# Title: KAIROS Orchestration Hybrid Implementation Hardening

**Problem Statement:**
While KAIROS architectural concepts exist, there is an ongoing need to harden the implementation of the Shared Task List, Teammate Mesh, and AutoDream pipeline across all operating modes (Cloud-Native Multi-Tenant PostgreSQL/Redis and Standalone Local SQLite), ensuring proper fallback and schema consistency.

**Research Report:**
Based on codebase inspection, `shared_tasks` handles task states via `FOR UPDATE SKIP LOCKED`. AutoDream embeddings are routed to `autodream_memories`. We must harden the backend APIs that consume these tables and ensure the hybrid storage wrappers fallback gracefully if vector extensions or Redis aren't present.

**Design Doc:**
Refer to `docs/architecture/kairos_hybrid_os_final_architecture.md` for the unified design on the Distributed State Machine (Task DAG), Teammate Mesh (real-time WebSocket/Redis PubSub), and AutoDream data pipelines (`pgvector`).

**Implementation Prompt:**
Implementer Agent, execute the following:
1. Review `docs/architecture/kairos_hybrid_os_final_architecture.md`.
2. Add unit tests covering the `FOR UPDATE SKIP LOCKED` degradation paths in `srcs/server/orchestration/tasks_test.go` (create if it does not exist) testing logic from `srcs/server/orchestration/tasks.go`.
3. Harden the `ProcessMemories` function in `srcs/server/orchestration/autodream_worker.go` to safely check for the vector extension before performing nearest-neighbor lookups, gracefully failing back to in-memory cosine similarity if necessary.
4. Validate that the Teammate Mesh broadcasts correctly in `srcs/server/api/mesh/sync_handler.go` even when the Redis client is unavailable, falling back to the Go memory transport.
